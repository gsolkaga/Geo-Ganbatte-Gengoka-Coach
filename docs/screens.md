# 画面の説明

3 つの画面それぞれの構造と、そうした理由。

> この文書は [README](../README.md) から切り出したものである。
**このリポジトリに画像は 1 枚も置かない**（Street View の画像はキャッシュ・再配布が禁止されている）。
スクリーンショットの代わりに、画面の構造と操作を文章で書く。

## 学習画面（`/`）

3 つの領域からなる。**横に 7 : 3 で割り、左が風景、右が観察欄である。**

```
[ 左 7 : 風景（Street View。4:3 固定）  ] [ 右 3 : 観察メモ 14 の欄 ]
[   開くと「回答」の板が下から重なる       ] [   ここは最後まで見える  ]
[ 閉じているときの帯（風景の外）          ]
-----------------------------------------------------------------
[ 全幅 : コードで確定した判定 → AI の解釈（採点後に下へ積む）       ]
```

## 風景の縦横比は 4:3 に固定してある

以前は「画面の残りを埋める」形だった。そのため**窓の大きさで縦横比が大きく変わり、
同じ地点でも見えている範囲が変わった。** 観察の練習にならない。

> **見る対象の形は、窓の形で決まってはならない。**

いまは幅から 4:3 で高さを出す。行の高さは左列が決め、右列がそれに従う。

**16:9 ではなく 4:3 にした。** 同じ幅で上下が広く見える。
観察するのは路面・ボラード・電柱・空であり、横に広いより縦に見えた方が
数えられるものが増える。

高さが伸びすぎないよう上限を置いているが、**上限は高さに掛けていない。**
`max-height` で止めると幅はそのままなので比率が崩れる
（`aspect-ratio` は幅と高さの両方が拘束されると無視される）。
代わりに**幅の上限を高さから逆算**している（`max-width: calc(78dvh * 4/3)`）。

> **比率を保ちたいなら、拘束するのは片側だけにする。**

### 縦積みのときだけ比率を諦める

`xl`（1280px）未満では左右に並べず縦に積む。そのとき風景は幅いっぱいなので、
4:3 だと**高さが幅の 3/4 になり、観察欄が画面の外まで押し下げられた。**

`max-xl:max-h-[55dvh]` で高さを止めている。幅は変えないので**比率は崩れる**
（4:3 より横長になる）。

比率を守るなら幅を絞ることになるが、そうすると**狭い画面で左右に余白ができる。**
それは直したばかりの問題である。

> **狭い画面では、比率よりも両方が見えることを採る。**

比率の保証は `xl` 以上、つまり**実際に練習する画面幅**で効く。

ページの横幅は 110rem まで許している。風景が幅から高さを決めるので、
**幅を許すほど風景が大きくなる。** ただし無制限にはしない
（観察欄の 1 行が長くなりすぎると読みにくい）。

## 余った場所は、埋めるのではなく、使うものに渡す

当初は 7 : 3 の固定列だった。風景の高さに上限があるため、
**低い窓では上限が先に当たり、風景が左列の中で中央に寄って
左右に説明のつかない余白ができた。**

列の幅を先に決めていたことが原因である。いまは `flex` にして、
左列は「望みの幅 68%、上限 `calc(78dvh*4/3)`」とし、**余りを右列が取る。**
余白が消えるだけでなく、観察欄が広くなる。

なお観察欄は**広い画面では絶対配置**で行の高さに従わせている
（14 の欄は 2,000px を超えるので、そのまま置くと行の高さを支配する）。
**狭い画面では通常の流れに戻して**内部スクロールさせる。

> **絶対配置は、親の高さが決まっている場所でしか使えない。**

**観察欄は最後まで見えている。** 回答するとき学習者は「自分が何を書いたか」を読み返すため、
回答欄を左下に置いて縦を詰めると読み返せなくなる。だから回答欄は風景の上に被せる。

> **被せてよいものと、被せてはいけないものを分ける。**

### 観察メモ（右列・14 の欄）

各欄は 3 つの状態から選ぶ。

| 状態 | 意味 |
|---|---|
| **見えた** | 写っていると判断した（そのとき素人語で記述する） |
| **見えない** | 写っていないと**判断した** |
| **未確認** | まだ見ていない、判断していない |

**「見えない」と「未確認」を分けているのが要である。**
「見えない」は判断の結果であり、「未確認」は観察漏れの候補である。
分からないものを「見えない」にすると、見落としの判定が狂う。

欄は `traffic_side`（走行帯）/ `road_marking`（路面標示）/ `bollard` / `pole`（電柱）/
`sign`（標識）/ `script`（文字）/ `ground`（地面）/ `terrain_vegetation`（地形・植生）/
`architecture`（建物）/ `vehicle`（車）/ `pavement`（舗装）/ `camera`（撮影車）/
`season`（季節・太陽）/ `other` の 14 個。

**記述は素人語でよい。** 「点が2つ付いた文字がある」と書けば、正規化が用語 ID に対応づける。

### 回答（下からスライドする板）

「回答を開く」で下から出てくる。**モーダルではない。**

- 背景を暗くしない（右の観察欄を読ませる）
- 焦点を閉じ込めない。`Tab` で外へ出られる
- `Escape` で閉じる
- 開くと見出しへ焦点が移り、閉じると開いたボタンへ戻る

中身は 4 つ。

1. **候補国**（最大 3 件、確信度つき。`high` は最大 1 件）
2. **決め手にした欄**

3. **採点に渡す情報**（**既定は `v2`**）
   - `v1` … 観察メモと回答だけを渡す。**正解タグも用語辞書も渡さない**（見落としの判定はできない）
   - `v2` … 正解タグと用語辞書も渡す。採点前に観察メモを用語 ID へ正規化する（**+1 リクエスト**）
   - **画面もプロンプト骨格も同一で、渡す情報だけが違う。** UI を分けると対照実験にならない
   - `v1` は**対照実験のために残してある選択肢**であり、学習に使うものではない。
     既定を `v1` にしていた頃は、初めて触った人が最も情報の少ない採点を受けていた
4. **採点に使うモデル**（既定 1 件。4 モデル同時は比較用の副機能）

下端に**閉じる**と**採点する**を並べてある。書き終わる場所は下端なので、
見出しの閉じるボタンまで戻らずに済む。**この行は無効化の対象外**にしてあり、
採点結果を表示中でも閉じられる（開けたのに閉じられない板を作らない）。

#### 候補国は押して選ぶ。国コードを打たせない

以前は `<input maxlength="2">` に `datalist` を添えていた。
つまり **`KZ` を知らないとカザフスタンを選べなかった。**
学習者が鍛えたいのは観察であって、ISO 3166-1 の暗記ではない。

> **入力の形式を覚えることが、練習の一部になってはいけない。**

いまは 102 カ国のグリッドで、押すと候補に入り、もう一度押すと外れる。
**「候補を追加」ボタンは消した。** 追加してから国を打つ流れだと、
**国が空のまま確信度だけ付いた候補**が作れてしまう。

> **選んでいないものが、選択肢の一覧に並んでいてはいけない。**

グリッドは**ドロップダウンの中に入れてある。** 最初は開いたまま並べていたが、
**閉じられないので 102 件が場所を取り続け、**確信度と採点ボタンが下へ押し出された
（実測 2026-08-19）。選ぶのは 1 プレイに 1〜3 回なので、必要なときだけ開く。

**地域でまとめるのはやめた。** 「北欧」「東欧」で括って地理順に並べた版を作ったが、
実際に使うと**却って探しにくかった。** 目当ての国がどの括りに入るかを
先に考える手が 1 つ増え、当て方を間違えると見つからない。

> **分類は、分類を知っている人にしか効かない。**

いまは五十音順の平らな並びで、絞り込み欄で詰める。
**順番を覚えなくても、頭の 2 文字を打てば出る。**

絞り込み欄は**日本語名の部分一致とコードの前方一致の両方**を見る
（`カザ` でも `KZ` でも引ける）。**コードは併記したまま残してある。**
選ぶのに要らなくても、目にし続けることで自然に覚える。

**国旗は出していない。** Windows では絵文字の国旗が表示されず、
外部 CDN を使うとオフラインで壊れる。そして**国旗は Street View に写る手がかりではない**ので、
観察の訓練には効かない。速く選べるようになるだけである。

閉じているときは帯に要約が出る。**開かないと何を答えたか分からない作りにしない。**

```
[回答を開く]  候補: 日本（high）　決め手: script　v2 / 2 リクエスト
```

**この帯は風景の外（枠の下）にある。** 当初は枠の中に重ねていたが、
開いていないときでも風景の下端を隠していた。被せてよいのは開いたときだけである。

> **常に出ているものを、見たいものの上に置かない。**

採点ボタンには**押す前に消費数が出る**（`v2 で採点する（2 リクエスト）`）。

### 採点後（下に積む）

上が**コードで確定した判定**、下が **AI の解釈**である。順序に意味がある。
学習者が「次に何を見ればよいか」を得るのはコード側なので、AI の解釈を上に大きく置かない。

コード側に出るもの。

```
正解と候補の突き合わせ / 見落とした欄 / 見落としではないもの（視認できない欄・
隣の欄に書いた観察・別ルートで正解したため不要だった欄）/ 欄ごとの絞り込み力（該当国数）/
達成された絞り込み（積集合）/ 次に見るべき欄（縮小量の昇順）
```

AI 側はモデルごとに独立した板になる。**採点中も描画する**（打ち切りの兆候が見えるため）。

### 画面上部

- **いま使っているデータセットと進捗**（`Standard 10　3 / 10 問`）
- 問題の移動（**採点せずに移動できる。入力は問題ごとに保持される**）
- 同じ行の右端に**過去の採点**の選択肢（**消費 0** で講評を読み返す）

過去の採点は当初ボタンを並べていたが、記録が増えると横幅を食って
問題移動が押し出された。**行の右端に寄せて 1 つにまとめた。**

### 過去の回答を戻す（観察欄の最上段）

**14 の欄を埋める労力を、採点 1 回で使い捨てない。** モデルや `v1`/`v2` を変えて
再採点するときに打ち直しをさせない。

以前は画面上部の独立した帯だったが、**書く場所から遠かった。**
「打ち直したくない」と思うのは書き始める瞬間なので、観察欄の真上に小さく置いてある。

選択肢は**出題 ID と保存日時だけ**にしてある。以前は `variant`・記述の件数・
候補国・用語 ID の有無まで並べていたが、40 件を超えると 1 行が長く、
**選ぶ判断に使わない情報で埋まっていた。**

`variant` を落としたのは、**戻すのが観察メモと回答だから**である。
v1 と v2 の違いは採点に何を渡したかであり、**入るスロットは同じ**なので、
ここで見せると「v2 の回答」という存在しない区別を作ってしまう。

> **選ぶための情報だけを出す。** 記録に入っている情報を全部出すことではない。

採点の記録を選ぶ方（**過去の採点**）は `variant` を残している。
あちらは採点結果そのものを読み返すので、v1 と v2 で中身が違う。

## 編集モード（`/admin`）

**教材そのものを作る画面である。** 2 つのことをする。どちらも**消費 0**（AI を使わない）。

| | 何をするか |
|---|---|
| **新しい問題集を作る** | 出題を空にして名前を付けて始める。**辞書は引き継ぐ** |
| **いまの問題集を編集する** | 地点を足し、14 スロットに正解タグを付ける |

以前の手順は「CLI で地点を登録し、`data/questions.json` を手で編集して 14 スロットを埋める」だった。
**これだと風景を見ながら書けない。** 別の窓で Street View を開き、JSON に戻って打つ。

とくに視認可能性（`recognition`）は**画面を見ないと判断できない項目**である。
「意識して探せば見える」のか「写っているが気づけない」のかは、その風景を見て決めるしかない。

> **判断に必要なものが見えていない場所で、判断させない。**

### 見た瞬間に、学習画面ではないと分かること

`SlotForm` を学習画面と共用している。**部品が同じなので画面を取り違える。**
取り違えたまま触ると、練習ではなく**教材が書き換わる。**

配色を分けてある（`main.css` の `--color-edit-*`）。

```
学習画面   白地 + スレート
編集モード 濃い藍 + 琥珀（1 色も共有しない）
```

明るさ違いにしなかったのは、**画面写真でも区別できるように**するためである。
上端には「編集モード」の帯を出したままにしてある（スクロールしても消えない）。

> **取り違えると教材が壊れる画面は、見た瞬間に違うと分かること。**

### 新しい問題集を作っても、辞書は変えない

出題を空にするだけで、`data/glossary.json` には**触らない。**

白紙から作ると辞書も空になり、用語を選べないのでタグ付けができない。
それ以上に、**辞書ごと作り直した問題集の結果は前の結果と比べられない。**
辞書が変われば別の道具である。

> **測るものを変えるときは、測る道具を変えない。**

触らないので `npm run fingerprint -- --verify` が一致したままになる。
これが**別の 10 問で測った結果を、同じ辞書の成績として読める根拠**である。

破壊的な操作なので形で縛っている。

```
名前と作成者は必須      「無題」で作れると、後から何の問題集か分からない
一段では作らせない      何が起きるかを並べた確認を出してから押させる
控えを取る              .backup/<日時>/ へ退避してから空にする
同じ ID があれば 409    黙って上書きしない
前の問題集は棚に残る    切り替えで戻せる（画面にも戻せることを書いてある）
```

> **戻る道がある操作にする。**

### タグ付けの画面

左に風景（4:3）、右に 14 スロット。
**`SlotForm` を `mode="admin"` で使い回している**ので、
学習者が書くのと同じ形でタグを付ける。形が違うと突き合わせが機械的にできない。

編集モードだけに出るものが 4 つある。

| | 何をするか |
|---|---|
| **確認済み** | スロットごとに人手で確認したことを記録する。**一括承認は作らない** |
| **見えるか**（`easy` / `hard` / `blind`） | 視認可能性。**既定値を置かない**（未設定のまま保存できない） |
| **用語**（該当国数つき） | 辞書からそのスロットの用語を選ぶ。該当国数を併記するので、粗い用語を選んだことに気づける |
| **決め手** | 候補を弁別できるスロット。「見えた」にしたものから選ぶ |

撮影年月も出る（タグ付けの補助）。**学習者には渡していない**（`QuestionForLearner` に含めていない）。

### 保存は 1 件でも誤りがあれば 1 件も書かない

検証は `shared/answer-key.ts` の純関数に置き、**画面とサーバの両方が同じ関数を使う。**
押してから 422 で弾かれるのではなく、**押す前に理由が並ぶ。**

止めるものと知らせるだけのものを分けている。

```
止める   未確認が残っている / 「見えた」なのに記述が空 / 視認可能性が未設定
         別スロットの用語が入っている / 辞書に無い用語 ID
知らせる 用語 ID が無い（後から normalize:keys でも埋められる）
         決め手が blind / 決め手が 1 件も無い
```

**用語 ID が無いことを誤りにしていない。** 誤りにすると、
用語が辞書に無いスロット（実測 52 件）のせいでタグが 1 件も保存できなくなる。

> **止めるべきものだけを止める。** 残りは見せて人間に決めさせる。

なお**用語を人手で選べるようにしたのは、消費 0 で済むからである。**
`npm run normalize:keys` は AI に任せる代わりに出題数ぶんのリクエストを使う。
タグ付けの時点で分かっているなら、そこで入れておけば枠を使わない。

### 地点の登録も同じ画面からできる

座標と国を入れると、**pano の解決と著作権表記の確認はサーバが行う**
（`POST /api/questions`。画像取得エンドポイントは呼ばない）。

国は**回答欄と同じドロップダウングリッド**から選ぶ。ここも国コードを打たせない。
`POST /api/questions` は `countries.json` に無い国コードを 400 で弾くので、
**自由入力はグリッドでは作れない誤りしか生まない。**

> **選択肢が決まっている欄に、自由入力を残さない。**

ただし**1 件だけ選ぶ形にしてある**（`single`）。回答欄の「最大 3 件」を
そのまま使うと、別の国に変えるのに外してから選ぶ 2 手になる。
**選び直しは 1 手であるべきである。**

**出題の登録とタグの保存で入口を分けてある**（`POST /api/questions` と `POST /api/answer-key`）。
1 つにまとめると、**タグを直すつもりで地点を作ってしまう**経路ができる。

> **書き込む対象が違うものは、入口を分ける。**

### 問題集を 1 つ作る手順

```bash
npm run fingerprint -- --verify   # 辞書が記録した時点と同じであることを先に確かめる
npm run dev                       # /admin を開く

# 画面で：
#   1. 「新しい問題集を作る」で名前と作成者を入れる（辞書はそのまま引き継がれる）
#   2. 「新しい地点を登録する」で座標を入れて出題を作る
#   3. 風景を見ながら 14 スロットにタグを付けて保存する（1 問ずつ）

npm run validate:keys             # 正解タグの検査（消費 0）
npm run normalize:keys            # 用語 ID を埋める。**出題数ぶん消費する**
                                  # 画面で用語を選んでいれば要らない
npm run combo                     # 到達可能性（消費 0）
npm run fingerprint -- --verify   # 辞書を変えていないことを最後にもう一度
npm run dataset -- export --name "..."   # dist/ggg-dataset.json が出る
```

`normalize:keys` を飛ばせるのが、**画面で用語を選べるようにした見返り**である。

**この画面は認証を持たない。公開ホスティングしないこと。**

## データセットの管理画面（`/datasets`）

配布されたデータセットを取り込み、切り替える。取り込み・切り替え・削除・出典表示が
1 画面に載っている。**すべて消費 0。**

取り込みは**枠の中へドラッグ**するか、**「ファイルを選ぶ…」**で開く。
素の `<input type="file">` は小さく、取り込みの入口だと分かりにくかったので
押せる大きさの領域にした。`<input>` は消さず視覚的に隠すだけなので、
**キーボードでも到達できる。**

詳細は [学習用データセットの配布と取り込み](#学習用データセットの配布と取り込み) を参照。
