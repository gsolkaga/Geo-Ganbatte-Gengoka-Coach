## 決定済みで再検討しない事項

議論し直すと時間を失う。根拠はすべて実測または規約の確認に基づく。

### 規約
- **Street View の画像を保存・キャッシュしない。** pano ID のみ無期限に保存可
- **画像を AI に送らない。** 規約上グレーであり、かつ学習者が受け身になる

- **Street View Static API の画像取得エンドポイントを呼ぶコードを書かない**（課金対象）
- `.gitignore` で画像拡張子を全除外済み。この設定を緩めない

### さくらの AI Engine（実測値）
- エンドポイント `https://api.ai.sakura.ad.jp/v1`
- アカウントトークンは `<UUID>:<シークレット>` 形式のまま `Authorization: Bearer` に渡す。**分離しない**
- **タイムアウトは約 300 秒。** 非公開・SLA 適用対象外・変更手段なし
- **HTTP 400 は消費されない。HTTP 504 は消費される。** 推論が走ったら消費
- **リトライしない。** 失敗は事実として記録する
- `response_format: json_schema` + `strict: true` は動作する
- **`strict: true` は件数を保証しない。** 構造だけである
- **`minItems` は配列ごとに指定が必要。入れ子に伝播しない**
- ストリーミングは **HTTP 200 のまま `finish_reason` なしで打ち切られる。** 必ず検証する
- 推論フィールドは `reasoning`（マニュアル記載の `reasoning_content` ではない）。**両方のキーを見る**
- `max_tokens` の既定値は 4,000 以上。推論が枠を消費する
- **RAG と embeddings は無償プランでも課金対象。使わない**
- モデル別実測: gemma 17〜19 秒 / gpt-oss 22〜27 秒 / Qwen3-0.6B-cpu 38〜45 秒 /
  Kimi 89〜300 秒超 / llm-jp はコンテキスト 4,096 で使用不可

## 1. `GradingResult` の判定不能：`| null` にする

**フラグを別に持たせる案は採らない。`SlotId[] | null` にする。**

`design.md` の `GradingResult` を更新済み。v1 で算出できないものを `null` にした。

```
discoveries        | null      正解タグが必要
missedSlots        | null      正解タグが必要
wrongAbsentSlots   | null      正解タグが必要
overclaimedSlots   | null      正解タグが必要
failureModes       | null      正解タグが必要
narrowingPower     | null      辞書が必要
intersection       | null      辞書が必要
nextPriority       | null      既に null 可（変更なし）

hit / hitConfidence / confusionPairs    v1 でも算出できる。null にしない
```

**理由。`[]` は「計算した結果、該当なし」、`null` は「計算できなかった」である。**
混ぜると v1 の採点が「見落としゼロ」と読める出力になる。**満点に見える誤りが最も悪い。**

これは `absent`（写っていない）と `unknown`（見ていない）を必ず区別するという
本アプリの中心規約と同じ構造である。**同じ規約を採点結果の型にも適用する。**

`judgmentUnavailable: boolean` を採らないのは、**フラグは無視できるが `null` は
TypeScript が分岐を強制する**ためである。型で防げるものを規律で防がない。

`failureModes` について。`confident_error` と `aware_of_gap` は正解タグなしでも
判定できるが、一部だけ埋めた配列を返すと「診断が済んだ」ように見える。
**v1 では配列全体を `null` にする。**

UI では「判定していない」と明示する。**空欄にしない。**

## 2. 採点でストリーミングを使う（前の回答を撤回）

**`callChatStream` を実装する。** 当初「実装しない」と回答したが撤回する。

撤回の理由。当初の反対理由は「失敗経路が増えて対照実験が汚れる」だったが、
**エラーの判定を人間が行い、自動リトライをしない**なら、隠れた消費も静かな汚染も起きない。
失敗は人間が見て判断する。**1 リクエスト無駄になることは許容する。**

### ストリーミングは速度のためではなく可観測性のために入れる

**タイムアウトは回避できない**（実測）。解くべき問題は別である。

```
非ストリーミング : 94 秒間なにも起きない → 学習者はハングと区別できない
ストリーミング   : 初バイト 1.2 秒       → 生きていることが分かる
```

これは体感の改善ではなく、**状態が観測できるかどうかの違い**である。

### 部分 JSON はパースしない

採点応答は `response_format: json_schema` の構造化出力である。
**途中まで届いた JSON はパースできない。**

```
{"missedSlots": ["bol      ← 画面に出しても意味がない
```

したがってこう実装する。

- **ストリームは進捗表示にのみ使う。パースは完了後に 1 回だけ行う**
- 部分 JSON を解釈しようとしないこと。増分パーサを導入しない
- **1 採点あたり 1 リクエストを維持する**（構造化部分と散文を分けて 2 回呼ぶ案は採らない）

### `content` と `reasoning` を別に数えて表示する

**ここが最も重要である。** 合計バイト数だけ出すと、何も生成していないのに健全に見える。

実測（`docs/generated-streaming/`）では Kimi がこうなった。

```
chunks=17,600  content=0 文字  reasoning=22,262 文字  → 303 秒で打ち切り
```

**17,600 個のチャンクが届いていて、生成物は 0 文字だった。**

| 画面に出す状態 | 人間の判断 |
|---|---|
| `content` が増えている | 正常。待つ |
| **`reasoning` だけ増えて `content` が 0** | **打ち切られる兆候。待つか中断かを選べる** |
| `finish_reason` なしで終了 | **失敗。生テキストを見て再採点を判断** |

### 実装の要件

`server/utils/ai.ts` に `callChatStream` を追加する。

1. **`finish_reason` の存在を必ず検証する。** 無い、または `length` の場合は打ち切りとして扱う
   - **HTTP 200 は成功を意味しない。** これが本プロジェクトで最も繰り返し確認された事実である
2. 戻り値に計測値を含める
   ```ts
   { status: 'ok' | 'truncated' | 'error'
     content: string          // 生の蓄積テキスト（パース前）
     reasoning: string
     finishReason: string | null
     chunks: number
     firstByteMs: number
     totalMs: number }
   ```
3. **打ち切りでも `data/usage.jsonl` に記録する。** リクエストは消費されている。
   `streamed: true` と `truncated: true` を残す
4. **自動リトライしない。** サーバ側で再送しない
5. **打ち切り時は蓄積した生テキストをクライアントへ返す。** 捨てないこと。
   パース不能でも人間は中身を読んで判断できる。**それが「判定は人間」の実装である**

UI 側。

- 生成中は `content` と `reasoning` の文字数を別々に表示する
- 打ち切り時は生テキストを折りたたみで表示し、**「再採点する」ボタンを出す**
- ボタンは人間が押す。**自動で再実行しない**
- 再採点は 1 リクエストを消費することを画面に明記する

### タスク 26 の比較スクリプトは非ストリーミングのままにする

**ここは変えない。**

- 誰も見ていないバッチ処理に失敗経路を増やす理由がない

### 記事に使える

これは章 11 のストリーミングの節を、実測から実装判断へ繋げる材料になる。

> HTTP 200 のまま打ち切られるという失敗の仕方は、**UI に出すと人間が判定できる。**
> 自動化すると静かに成功として通る。

**打ち切りの検出をコードが行い、続行の判断を人間が行う。** 責務境界の話と同じ構造である。

## 3. プロンプトテンプレートは 1 か所に置く：承認

# 追加決定：再採点と 4 モデル同時採点

プレイヤー視点からの指摘による。**14 スロットを埋める労力に対し、採点 1 回で
使い捨てるのは不経済である。** 同じ観察メモをモデルを替えて再採点できるようにする。

`tasks.md` にタスク **26.1**（再採点と同時採点）と **26.2**（同時実行数の測定）を追加した。
タスク 13 も更新した。

## 位置づけ：新機能ではなくタスク 26 の UI 化

v1/v2 比較は「同じ観察メモを条件を変えて再採点する」機能であり、
**モデル差し替えと同じ機構である。** 別々に作らない。

再採点を UI 機能にすれば、タスク 26 がスクリプトではなく画面操作になる。
**これで締切内に収まる。** 新規に作るのは `models: string[]` の受け口と並列描画だけである。

## 画面の構造は責務境界に従う

**ここが設計の中心である。**

```
1 回だけ表示（モデルに依存しない）
  hit / hitConfidence / confusionPairs / missedSlots / wrongAbsentSlots
  overclaimedSlots / narrowingPower / intersection / nextPriority
        ↑ すべてコードが計算する。モデルを替えても変わらない

モデルごとに並べる
  feedback   ← AI の解釈。ここだけが変わる
```

**確定している事実は 1 つ、解釈は複数。** これをレイアウトで示す。

コード算出分を 4 回繰り返して表示しないこと。**同じ値が 4 つ並ぶと、
それが計算結果であることが伝わらない。**

## 並列とパネル独立描画は必須条件

**全件揃うまで待つ実装にしないこと。**

```
gemma    17〜19 秒
gpt-oss  22〜27 秒
Qwen     38〜45 秒
Kimi     89〜300 秒超（しばしば finish_reason なしで打ち切り）
```

揃うまで待つと最も遅いモデルに引きずられ、**Kimi が失敗すると画面全体が失敗に見える。**

パネルごとに独立してストリームし、独立して完了・失敗させる。
**ストリーミングの実装がここで報われる。** 速度と精度の逆相関を、待っている間に体験できる。

失敗したパネルは、そのパネルだけに生テキストと「再採点する」ボタンを出す。
**他のパネルの結果を消さないこと。**

## やってはいけないこと

**モデル間の不一致を「あなたの記述が曖昧です」として提示しないこと。**

そう言いたくなるが、根拠がない。ボラード実験で、**学習者のメモが一切介在しない
事実問題でも、3 分の 2 の国でモデル同士が食い違った**（`docs/bollard-axes-conclusion.md`）。

```
素材          42/64 カ国でモデル間不一致
反射板の色    43/64 カ国でモデル間不一致
```

不一致はモデル側のノイズと交絡している。**記述の曖昧さの指標として使えない。**

出せるのは「解釈は一致していない」という事実の提示までである。**原因の帰属はしない。**

これは本プロジェクトで繰り返し確認してきたことと同じ規律である。
**モデル間の一致は正しさを保証せず、不一致は原因を特定しない。**

## タスク 26.2：同時実行数の上限を先に測る

**さくらの AI Engine の同時実行数の上限は非公開である**（タイムアウトと同じ）。

タスク 26.1 の実装前に 4 リクエスト使って測ること。

| 確認する項目 | 結果によってどうするか |
|---|---|
| HTTP 429 が返るか | 返るなら直列＋進捗表示に落とす |
| キューされて直列と同じ総時間になるか | そうなら並列の意味がないので直列にする |
| 並列で本当に短縮されるか | 短縮されるなら 26.1 を並列で実装する |

**結果を `docs/` に記録すること。記事の実測材料になる。**
非公開の制約を実測で明らかにするのは、この記事の柱の 1 つである。

## タスク 13 の変更：v1 の採点は 4 モデル全部で取る

**1 モデルで済ませないこと。**

1 モデルが当たり障りのない褒め言葉を返すより、**4 モデルが揃って中身のないことを言う**方が
証拠として決定的である。「モデルを替えれば解決する」という反論を先に潰せる。

**v1 の出力は再現できない。** 後から 4 モデル分を取り直すことはできない。

消費は 3〜10 プレイ × 4 モデル = 12〜40 リクエスト。B の枠 700 に対して問題ない。

## 実装順序

```
26.2（同時実行数の測定、4 リクエスト）
  ↓ 並列が有効かを確認してから
10 → 11 → 12 → 13（v1 の記録。4 モデルで取る）
  ↓
26.1（再採点 UI）
```

**26.2 を先にやること。** 並列が使えないと分かってから 26.1 を書き直すのは無駄である。

ただし **13 の優先度が最も高い。** 26.1 が間に合わなくても、
13 で 4 モデル分の v1 出力が取れていれば記事は書ける。
**26.1 は「取れたものを見やすく並べる画面」であり、データの取得は 13 で完結する。**

## 補足：既定は 1 モデル。画面の優先順位を守る

タスク 26.1 に条件を追加した。`design.md` にも「画面の優先順位」の節を追加した。

### 目的の再確認

**本アプリの目的は、学習者が「何を見て、何を言語化すれば国当ての精度が上がるか」を
得ることである。AI の解釈はその手段の一部であり、全体ではない。**

**採点とコーチングであって、審判ではない。**

### 画面の優先順位

| | 内容 | 学習者に与えるもの |
|---|---|---|
| **主** | 見落としスロット、絞り込み力、積集合、次に見るべきスロット | **何を見ればよかったか。次にどこを見るか** |
| **従** | `feedback` | 素人語と正規用語の橋渡し、失敗モードの説明 |

**`feedback` を最上部に大きく置かないこと。**

コード算出分は**モデルを替えても変わらず、検証可能である**。`feedback` は変わる解釈である。
**変わらないものを主に、変わるものを従に置く。**

責務境界を画面の情報設計にも適用する、という話である。

### 同時採点は既定にしない

**既定は 1 モデル。** 4 モデル同時は明示的に選んだときだけ動かす。

**学習者の注意が AI の比較に向くと目的から逸れる。**
風景を観察する訓練のはずが、AI の出力を観察する時間になる。

同時採点が最も価値を持つのは **v1** である。中身のない励ましが 4 通り並ぶことに意味がある。
v2 ではコード算出分が主役であり、並列表示の必要性は下がる。

**タスク 13（v1 の記録）では 4 モデルで取る。日常の学習では 1 モデルで足りる。**
