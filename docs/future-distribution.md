# 将来の方向：問題セットの配布とデータセットの評価

**今回のスコープ外である。実装しない。** 現在の設計が何を可能にしていて、
何を決めておかないと後で高くつくかを記録する。

## 構想

ユーザーが作成した問題セットを配布し、他のプレイヤーが取得して**自分の AI で**
コーチングを受けられるようにする。

コーチング役の AI は各自が持ち込む。**アプリは問題セットと辞書と計算を提供し、
解釈は利用者の環境で行う。** 現在の責務境界をそのまま分散させた形になる。

## 規約の制約が、結果として配布可能性を作っていた

**問題セットに画像が 1 枚も含まれない。**

```
questions.json に入るも
  panoId  座標  country  copyright  captureDate  正解タグ（slots）
```

pano ID の保存は Google Maps Platform の規約で明示的に許容されている。
**この形式なら配布できる。**

**画像をキャッシュする設計にしていたら、配布は規約違反で不可能だった。**
規約を読んで設計を変えた判断が、そのまま共有可能性になっている。

`.gitignore` で画像拡張子を全除外しているため、**誤って画像を同梱することが機械的に防がれている。**

## 問題セット単体では配布できない

**ここが設計上の核心である。**

```
正解タグ    = 用語辞書の用語 ID       ← 辞書がないと意味を持たない
絞り込み力  = 該当国数 / 母集団       ← 母集団が違うと数値が変わる
```

**同じ問題セットが、辞書と対象国リストを替えると違うフィードバックを出す。**

したがって配布単位は「問題セット」ではなく、**「問題セット ＋ 辞書 ＋ 母集団」**である。

| 配布物 | 依存 |
|---|---|
| `questions.json` | `glossary.json` の用語 ID、`countries.json` の母集団 |
| `glossary.json` | `countries.json` の母集団（`countries` の件数が絞り込み力になる） |
| `countries.json` | なし（ただし出題範囲と一致していなければならない） |

`curriculum.md` に既に書いてある注意がここに繋がる。

> カバレッジのない国を母集団に入れると絞り込み力が過大になり、実態とズレる

**母集団は数値の分母である。** バンドルするか、バージョンで参照するかを決める必要がある。

## データセットの評価は 2 層に分かれる

| 検証 | できるか | 方法 |
|---|---|---|
| **整合性** | **できる。コードだけで確実** | 集合演算 |
| **正しさ** | **できない** | 人間が Street View を見る |

### 整合性の検証は今すぐ作れる（AI を使わない）

配布されたセットに対して機械的に判定できる。

- 正解タグの用語 ID が辞書に存在するか（**存在しなければ不正**）
- 決め手スロットとされた用語の該当国に、正解国が含まれているか
- **全用語の該当国の積集合に、正解国が含まれているか**
  - 含まれなければ**タグが矛盾している**。集合演算だけで確定的に言える
- 難易度の申告と、実際の絞り込み力が整合しているか
- `panoId` のメタデータ照会で、著作権表記が Google 提供か（**無料・クォータ消費なし**）
- 画像ファイルが同梱されていないか

**「積集合に正解国が入らない問題セット」は機械的に不正と判定できる。**
配布物の品質フィルタとしてこれだけで相当機能する。

これは本アプリの採点ロジックと同じ機構である。**学習者の回答を検証する仕組みが、
そのままデータセットを検証する仕組みになる。**

### 正しさの検証は、今回の実験で限界を測ってしまった

複数モデルの突き合わせは**候補を挙げられるが裁定できない。**

| 事例 | 票 | 結論 |
|---|---|---|
| ルーマニアの文字体系 | 4/4 一致 | 人間が誤っていた（**使える信号**） |
| ガーナの走行車線 | 3/4 一致 | AI 3 モデルが誤っていた（**多数決が誤り**） |
| ボラードの属性値 | **一致 0 件** | **信号がない** |

**4/4 一致だけが使える信号であり、割れたら情報がゼロである。**
ボラードでは 4/4 一致が 1 件も出なかった（`docs/bollard-axes-conclusion.md`）。

したがって配布物の正しさは、**自動判定できない。** 人手のレビューか、
利用者の評価の蓄積に頼ることになる。**そこは技術ではなく運用の問題である。**

## 「正しいデータセットを配布する神」について

**Plonk It が既にその神である。** コミュニティがキュレーションしたデータセットとして成立している。

期待すべきは新種の出現ではなく、**Plonk It が持っていない層を足すこと**である。

| | Plonk It | 用語 ID と集合として持つ場合 |
|---|---|---|
| 記述 | 散文。人間が読んで理解する | 構造化。**機械が矛盾を検出できる** |
| 粒度 | 極めて細かい | 辞書の粒度に依存する |
| 検証 | 執筆者と読者による | **整合性は自動、正しさは人手** |

**散文では整合性の自動検証ができない。** ここが構造化する価値である。

ただし逆も成り立つ。**構造化すると粒度が落ちる。**
「トレッカーの横を歩く人物の T シャツの色」は 14 スロットに収まらない
（`other` スロットが受け皿として置かれている理由）。

## 今のうちに決めておくと安いこと

**現時点では変更しない。** B が `data/questions.json` を扱うタスク 12 を実装中であり、
形式を今変えると衝突する。**タスク 12 の完了報告を受けてから判断する。**

### 1. `questions.json` にラッパーを付けるか

現在は配列である。配布を想定するとメタデータを持たせたくなる。

```json
{
  "schemaVersion": 1,
  "slotSchemaVersion": 1,
  "requires": { "glossary": "...", "countries": "..." },
  "author": "...",
  "license": "CC BY 4.0",
  "questions": [ ... ]
}
```

**配列からオブジェクトへの変更は破壊的である。** 保存済みファイルが増えてからやるほど高くつく。
ただしタスク 12・13 が終わるまでは触らない。**13 の記録を失うリスクを取らない。**

### 2. スロット定義のバージョン

**スロット ID が変われば古いセットが壊れる。** 14 スロットは確定しているが、
`other` が「まだ言語化されていない観察の受け皿」であるため、
**将来スロットが増える設計になっている**（ルワンダの清潔さで実際に増えた）。

増えたときに古いセットをどう扱うかを決める必要がある。

### 3. 帰属表示

`LICENSE-DATA` で人手記述を CC BY 4.0 としている。**CC BY は帰属表示を要求する。**
配布物にメタデータがなければ、受け取った側は帰属できない。

## 実装しない理由

- **8/20 の記事公開までに v1/v2 の対照実験を完成させることが最優先である**
- 配布機能は**利用者が複数いて初めて意味を持つ**。現時点で利用者は 1 人である
- 整合性の検証は作れるが、**検証すべき配布物が存在しない**

**先に必要なのは、1 人が使って学習効果があるかどうかの確認である。**
