# Requirements Document

## Introduction

Street View 上の風景を見て、気づいた特徴を言語化し、その言語化の質を AI が採点・添削する Web アプリ。GeoGuessr の世界マップ学習者を対象とする。

「AI が画像を見て場所を当てる」アプリではない。**画像を見るのは人間**であり、AI は人間が書いた観察メモを解釈・評価する役に限定する。

### 背景となる問題認識

GeoGuessr で伸び悩む原因は 3 つに分解できる。

1. **観察漏れ** — 手がかりが写っているのに見ていない
2. **知識欠落** — 見えているが、それが何を意味するか知らない
3. **想起失敗** — 知っているが、その場で思い出せない

いずれも画像認識の問題ではなく、テキストで扱える問題である。本アプリはこの 3 つを切り分けて診断することを目的とする。

### 検証したい仮説

**学習ツールの品質は、AI の性能ではなく、人間が用意した正解データの質で決まる。**

この仮説を、UI とプロンプトを固定したまま教材データの有無だけを変える対照実験（v1 / v2）で検証する。

### スコープ

含むもの。

- Street View 埋め込みによる出題
- 11 スロットの構造化観察入力
- 素人語の正規化
- 見落とし判定と採点
- 失敗モードの診断とフィードバック
- 教材データの作成・編集（管理モード）
- 用語辞書
- v1 / v2 の対照実験
- リクエスト消費量の計測
- モデル比較検証
- 仕様書生成の比較検証

含まないもの。

- 間隔反復による再出題スケジューリング
- ユーザー認証・複数ユーザー対応
- 画像の保存・配信
- AI による画像認識
- 音声入力・音声読み上げ
- Mapillary 連携（構想として記録するのみ）
- 対戦モード、混同マトリクス可視化（余力がある場合のみ）

### スロット定義

観察対象は以下の 14 種類に固定する。ラベルは初心者が理解できる平易な表現を主とし、正規用語を括弧で添える。

| ID | 表示ラベル | 入力例 |
|---|---|---|
| `traffic_side` | 走行車線（右側／左側） | 右側通行 |
| `road_marking` | 道路の白線・黄線（路面標示） | 白の破線センターライン、路肩線なし |
| `bollard` | 車道脇の短い杭・ポール（ボラード） | 白い本体、上が黒、赤い反射板 |
| `pole` | 電柱・街灯の形 | コンクリ柱、逆 L 字アーム |
| `sign` | 標識の形・色 | 三角形、白地に赤縁 |
| `script` | 看板の文字（読めなくて OK、形を書く） | A の上に点が 2 つ |
| `ground` | 地面・土の色 | 赤茶色の土、白い砂 |
| `terrain_vegetation` | 地形・植生 | 急峻な山、乾燥した低木 |
| `architecture` | 建物・屋根の形 | 赤い瓦屋根、白壁 |
| `vehicle` | 車・ナンバープレート | 黄色の細長いナンバー |
| `pavement` | 車道の舗装 | 未舗装、補修痕だらけ |
| `camera` | 撮影車・カメラ世代 | 車体の映り込みあり、画質が粗い |
| `season` | 季節・太陽 | 落葉している、影が短い |
| `other` | その他の気づき | ゴミがまったく落ちていない |

`other` は他のどのスロットにも入らない観察の受け皿である。用語辞書に該当用語を持たないため正規化は常に「該当なし」となり、記述は辞書追加候補として蓄積される。**辞書を育てる入口として機能する。**

`other` を設けた理由は、既存のスキーマに収まらない観察が実在することが判明したためである（例：ルワンダはゴミが落ちていない）。

`ground` を `terrain_vegetation` から分離しているのは意図的である。統合すると、学習者が地形を記述した時点でスロットが埋まり、土の色の見落としを検出できなくなる。`season` を `camera` から分離しているのも同じ理由による。

各スロットは以下の状態を持つ。

- `visible` — 写っていると判断した
- `absent` — 写っていないと判断した
- `unknown` — 判断していない（未入力）

`absent` と `unknown` は必ず区別する。前者は判断の結果であり、後者は観察漏れの候補である。

## Glossary

| 用語 | 定義 |
|---|---|
| メタ | 地理的な場所を特定するための視覚的手がかり（ボラードの意匠、路面標示の色、文字体系など） |
| スロット | 観察対象のカテゴリ。13 種類を定義する |
| 候補集合 | 学習者が挙げた回答国の集合。最大 3 件 |
| 確信度 | 各候補国に付ける 3 段階（高・中・低）の自己評価 |
| 絞り込み力 | ある手がかりが候補を何カ国まで絞れるか。用語辞書の関連国の件数から算出する。内部の数値としてのみ使う |
| 最強メタ | 1 カ国に確定する手がかり。GeoGuessr コミュニティの語彙 |
| 強メタ | 2 カ国に絞れ、かつ地理的に近い手がかり |
| 良メタ | 3〜4 カ国に絞れ、かつ地理的に近い手がかり。失点が小さい |
| 補助メタ | 5 カ国以上、または大陸をまたぐ手がかり。単独では主役になれず、組み合わせが必須 |
| 地域グループ | メタの強さの判定に用いる地理的な近さの区分。`regions.json` に定義する |
| 候補集合の積集合 | 学習者が挙げた複数の用語の関連国の積集合。実際に達成された絞り込みを表す |
| 確定手がかり | 積集合を 1 カ国にできる未観察の手がかり |
| 弁別スロット | 候補集合に含まれる国どうしを区別できるスロット |
| 混同ペア | 学習者が同一回答内で併記した国の組。区別できていない国の組を示す |
| 素人語 | 正規の用語を知らない学習者が使う記述（例：「A の上に丸」） |
| 正規用語 | 用語辞書に登録された正式な呼称（例：「Å（A リング）」） |
| 正規化 | 素人語を正規用語の ID に対応づける処理 |
| 正解タグ | 出題地点に実際に写っている手がかりを、人間が確認して記録したデータ |
| 用語辞書 | 正規用語とその素人語表現・別名・関連国を収録したデータ |
| pano ID | Street View のパノラマを一意に識別する値。保存が許容されている |
| v1 | 正解タグと用語辞書を持たない版 |
| v2 | 正解タグと用語辞書を持つ版 |
| 失敗モード | 観察漏れ・知識欠落・想起失敗のいずれか |

## Requirements

### 要件 1：出題

**ユーザーストーリー**

学習者として、ランダムな地点の Street View を見て観察したい。自由に視点を動かせる必要がある。

**受入基準**

1. アプリが出題を表示する場合、システムは Street View を埋め込み形式で表示すること
2. 出題を表示する場合、システムは学習者が視点を回転・移動できる状態で表示すること
3. 画像を扱う場合、システムは Street View の画像データを保存・キャッシュしないこと
4. 出題データを保持する場合、システムは pano ID・座標・正解国のみを保存すること
5. 出題を読み込む場合、システムは pano ID の有効性を無償のメタデータ問い合わせで確認すること
6. pano ID が失効している場合、システムは保存済みの座標から再解決を試みること
7. 再解決も失敗した場合、システムはその出題をスキップし、失効を記録すること
8. 出題候補を採用する場合、システムはメタデータの著作権表記が Google 提供であることを条件とすること
9. 著作権表記が Google 以外である場合、システムはその候補を採用せず、理由を記録して除外すること

### 要件 2：構造化観察入力

**ユーザーストーリー**

学習者として、見えたものだけを該当欄に書きたい。すべてを自由文でゼロから書くのは負担が大きい。

**受入基準**

1. 観察入力を表示する場合、システムは 11 スロットを個別の入力欄として提示すること
2. 各スロットを表示する場合、システムは `visible` / `absent` / `unknown` を選択できる操作を提供すること
3. スロットラベルを表示する場合、システムは平易な表現を主とし正規用語を併記すること
4. 各スロットを表示する場合、システムは記述の粒度を示す入力例を提示すること
5. 学習者が `visible` を選んだ場合、システムは自由記述欄を有効化すること
6. 回答を確定する場合、システムは 1 件以上の回答国の入力を必須とすること
7. 回答国を入力する場合、システムは最大 3 件までの候補を受け付けること
8. 各候補を入力する場合、システムは確信度（高・中・低）の指定を必須とすること
9. 確信度を指定する場合、システムは「高」を 1 件までに制限すること
10. 回答を確定する場合、システムは決め手にしたスロットの指定を候補全体で 1 件求めること
11. 回答を確定する場合、システムは総合的な推論の自由記述欄を任意項目として提供すること

### 要件 3：素人語の正規化

**ユーザーストーリー**

学習者として、正規の用語を知らなくても観察を伝えたい。「A の上に丸」と書いても理解されるべきである。

**受入基準**

1. 学習者の記述を受け取る場合、システムは AI を用いて用語辞書内の用語 ID へ対応づけること
2. 正規化を実行する場合、システムは出力を用語辞書に登録済みの ID に限定すること
3. 辞書内に該当する用語が存在しない場合、システムは「該当なし」を返すこと
4. 「該当なし」が返された場合、システムはその記述を辞書追加候補として記録すること
5. 正規化に失敗した場合、システムは辞書外の用語を新規に生成しないこと
6. 正規化結果を保持する場合、システムは学習者の原文と対応づけた用語 ID の両方を保存すること

### 要件 4：見落とし判定

**ユーザーストーリー**

学習者として、何を見落としたのかを正確に知りたい。写っていないものを「見落とし」と言われては困る。

**受入基準**

1. 見落としを判定する場合、システムは AI を使用せず正解タグとの差分計算のみで判定すること
2. 正解タグに存在するスロットが学習者側で `unknown` である場合、システムはそれを見落としとして記録すること
3. 正解タグに存在するスロットが学習者側で `absent` である場合、システムはそれを誤った不在判断として記録すること
4. 正解タグに存在しないスロットを学習者が `visible` とした場合、システムはそれを過剰申告として記録すること
5. 正解タグが存在しない出題の場合、システムは見落とし判定を実行せず、判定不能であることを明示すること

### 要件 5：採点とフィードバック

**ユーザーストーリー**

学習者として、自分の観察と推論のどこが良くてどこが悪かったのかを具体的に知りたい。

**受入基準**

1. 回答を判定する場合、システムは AI を使用せず、正解が候補集合に含まれるかと、その候補の確信度をコードで判定すること
2. スロット記述の正確性を評価する場合、システムは AI を用いて評価すること
3. フィードバックを生成する場合、システムは正解タグに記載された手がかりのみを「この地点に写っている」と断定すること
4. 用語辞書由来の知識を用いる場合、システムはそれを地域一般の傾向として述べ、当該地点の事実として断定しないこと
5. 次に注目すべきスロットの優先順位を提示する場合、システムは AI を使用せず、正解タグと用語辞書から積集合の縮小量を計算して決定すること
14. 正解タグが与えられていない場合（v1）、システムは積集合の縮小量を計算できないため、優先順位の算出方法が異なることを記録すること
6. 見落とした手がかりを説明する場合、システムはその手がかりが持つ絞り込み力を件数とともに提示すること
10. 採点結果を提示する場合、システムは学習者が決め手に選んだスロットのメタの強さを提示すること
15. メタの強さを判定する場合、システムは該当国数と地理的な散らばりの 2 軸で判定すること（同じ件数でも大陸をまたぐ場合は失点が大きいため）
16. メタの強さを提示する場合、システムは該当国数と地域のまたぎ方を併記すること
17. リージョン（国内の地域）レベルの絞り込みは対象外とすること。用語辞書の関連国が国コードのみであるため構造的に対応していない
11. 学習履歴を提示する場合、システムは決め手に選んだスロットのメタの強さの推移を示すこと（探索順序の判断が改善しているかを測る指標であるため）
12. 経過時間を上達の指標として扱わないこと（記述量とタイピング速度に依存し、観察の改善が数値の悪化として現れるため。速度は実戦で鍛え実戦で測る）
13. メタの強さを表示する場合、システムは GeoGuessr コミュニティの語彙（「強いメタ」「弱いメタ」）を用い、該当国数を併記すること。独自の用語を用いないこと
7. 候補集合が複数の国を含む場合、システムは正解タグの決め手スロットを弁別スロットとして提示すること
8. 候補集合が複数の国を含む場合、システムはその組を混同ペアとして記録すること

### 要件 6：失敗モードの診断

**ユーザーストーリー**

学習者として、自分が「見ていない」のか「知らない」のか「思い出せなかった」のか「絞り込めたが決められなかった」のかを区別したい。原因が違えば対策も違う。

**受入基準**

1. 診断を実行する場合、システムは観察漏れ・知識欠落・弁別失敗・自信のある誤りのいずれに該当するかを判定すること
2. 正解タグにある手がかりが `unknown` である場合、システムは観察漏れと判定すること
3. 正解が候補集合に含まれず、かつ最高確信度が「高」である場合、システムは自信のある誤りと判定し、最優先の修正対象として提示すること
4. 正解が候補集合に含まれ、かつその確信度が「中」または「低」である場合、システムは弁別失敗と判定すること
5. 正解が候補集合に含まれず、かつ全候補の確信度が「低」である場合、システムは手がかり不足を自覚できている状態として、観察漏れまたは知識欠落のどちらに起因するかを提示すること
6. スロット記述が正確でありながら正解が候補集合に含まれない場合、システムは知識の紐付け失敗と判定すること
7. 診断結果を提示する場合、システムは該当する失敗モードごとに異なる助言を提示すること
8. 学習者の `other` の記述が正解タグの `other` に対応する場合、システムはそれを失敗モードとして扱わず、発見の記録として提示すること
9. `other` に記述があった場合、システムはその内容を辞書追加候補として最優先で記録すること

### 要件 7：教材データの作成

**ユーザーストーリー**

教材作成者として、出題地点に写っているものを正確に記録したい。下書きがあると助かるが、鵜呑みにはしたくない。

**受入基準**

1. 管理モードを提供する場合、システムは学習モードと同一のスロット入力コンポーネントを使用すること
2. 下書きを生成する場合、システムは国定数テーブル・AI 生成の順に候補を埋めること
3. 下書きを表示する場合、システムは未確認であることが視覚的に区別できる表示にすること
4. 教材データを保存する場合、システムは全スロットが確認済みまたは明示的にクリアされていることを条件とすること
5. 管理モードを提供する場合、システムは全スロットを一括承認する操作を提供しないこと
6. 教材データを保存する場合、システムは決め手となるスロットの指定を必須とすること
7. 教材データを保存する場合、システムは難易度の指定を必須とすること

### 要件 8：用語辞書

**ユーザーストーリー**

開発者として、素人語と正規用語の対応を管理したい。辞書の誤りは学習者に誤った知識を与える。

**受入基準**

1. 用語辞書を保持する場合、システムは正規用語・平易な表現・別名・関連国・混同しやすい用語を記録すること
2. 関連国を記録する場合、システムは複数国を許容すること（同一の手がかりを共有する国が存在するため）
3. 絞り込み力を算出する場合、システムは AI を使用せず関連国の件数から算出すること
8. 学習者が複数の用語を挙げた場合、システムは AI を使用せず関連国の積集合を算出すること
9. 積集合を提示する場合、システムは単独では弱いメタでも組み合わせにより決定的になりうることを示すこと
4. 辞書を生成する場合、システムは複数モデルに同一の指示を与えて生成させること
5. 複数モデルの出力が一致しない場合、システムはその項目を人手確認対象として記録すること
6. 辞書項目を採用する場合、システムは人手確認を経たことを記録すること
7. 辞書を提示する場合、システムは学習者が閲覧できる用語集として表示すること

### 要件 9：v1 / v2 の対照実験

**ユーザーストーリー**

記事執筆者として、教材データの有無が学習体験にどう影響するかを厳密に比較したい。

**受入基準**

1. 実験を実施する場合、システムは v1 と v2 で同一の出題セットを使用すること
2. 実験を実施する場合、システムは v1 と v2 で同一の観察メモを入力として使用すること
3. 実験を実施する場合、システムは v1 と v2 で同一の UI・同一のプロンプト骨格を使用すること
4. v1 で動作する場合、システムは正解タグと用語辞書を参照しないこと
5. v2 で動作する場合、システムは正解タグと用語辞書を参照すること
6. 比較を記録する場合、システムは両版の採点結果を並べて保存すること
7. v1 の実行結果を得た場合、システムはその出力を後から参照可能な形で保存すること

### 要件 10：リクエスト消費量の計測

**ユーザーストーリー**

記事執筆者として、3,000 リクエストが何にどれだけ消えたのかを正確に報告したい。

**受入基準**

1. AI へ問い合わせる場合、システムは用途分類・モデル名・時刻を記録すること
2. 計測を記録する場合、システムは用途を「アプリ実行」「辞書生成」「知識検証」「下書き生成」「モデル比較」に分類すること
3. 計測結果を提示する場合、システムは分類ごとの合計を出力すること
4. コーディングエージェント経由の消費については、システムの計測対象外とし、コントロールパネルの利用量スナップショットで別途記録すること

### 要件 11：規約・ライセンス制約

**ユーザーストーリー**

開発者として、外部サービスの規約に違反しない設計にしたい。

**受入基準**

1. Street View の画像を扱う場合、システムは画像データを保存・キャッシュ・再配布しないこと
2. Street View の画像を扱う場合、システムはその画像を外部の AI サービスへ送信しないこと
3. 出題データを保存する場合、システムは保存が許容されている pano ID と座標に限定すること
4. Street View を表示する場合、システムは提供元の帰属表記を改変・隠蔽しないこと
5. 第三者の画像を利用する場合、システムはライセンスと撮影者クレジットを記録すること
6. リポジトリを公開する場合、システムは画像ファイルを一切含めないこと
7. 出題を選定する場合、システムは外部の個人が投稿したパノラマを採用しないこと（権利者が投稿者であり、Google 提供の画像とは権利関係が異なるため）
8. 出題データを保存する場合、システムはメタデータから取得した著作権表記を記録すること

### 要件 12：認証情報の保護

**ユーザーストーリー**

開発者として、API キーを漏洩させたくない。

**受入基準**

1. AI へ問い合わせる場合、システムはサーバ側の処理を経由し、ブラウザに API キーを露出させないこと
2. 地図サービスの API キーを使用する場合、システムは参照元ドメインによる利用制限を設定すること
3. リポジトリを公開する場合、システムは API キーを含むファイルを除外し、雛形のみを配置すること

### 要件 13：モデル比較検証

**ユーザーストーリー**

記事執筆者として、添削役に向くモデルを実測で選びたい。

**受入基準**

1. 比較を実施する場合、システムは同一の観察メモと同一の出題を複数モデルに与えること
2. 比較を実施する場合、システムはモデル名・実行日時・パラメータを記録すること
3. 比較結果を提示する場合、システムは指摘の正確性・具体性・誤指摘の有無を評価軸とすること
4. 世界メタの知識精度を検証する場合、システムは複数の国・複数の観点について正解と照合可能な形で問い合わせること
5. 知識精度の検証結果を記録する場合、システムは誤答の実例を原文のまま保存すること

### 要件 14：仕様書生成の比較検証

**ユーザーストーリー**

記事執筆者として、AI が設計時に規約上の制約を考慮するかを実測したい。

**受入基準**

1. 検証を実施する場合、システムは同一の要求文を複数モデルに与えること
2. 検証を実施する場合、システムは各モデルについて複数回試行すること
3. 生成結果を評価する場合、システムは外部サービスの規約への言及有無を評価軸に含めること
4. 生成結果を評価する場合、システムは AI とコードの責務分離の提案有無を評価軸に含めること
5. 検証結果を公開する場合、システムは要求文・生成物の全文・評価基準・実行条件を含めること
6. 生成結果を報告する場合、システムは要約ではなく原文を保存すること

## 優先順位

実装が間に合わない場合、以下の順に切り捨てる。

1. 対戦モード、混同マトリクスの可視化（データの記録自体は要件 5-8 で行うため、切り捨てるのは表示のみ）
2. Mapillary 連携
3. 出題数（20 問 → 15 問 → 10 問）
4. モデル比較の対象モデル数
5. 教材データの下書き自動生成（手入力で代替）

以下は切り捨て不可。これらが欠けると検証が成立しない。

- 要件 3（正規化）
- 要件 4（見落とし判定）
- 要件 9（v1 / v2 対照実験）
- 要件 13 の知識精度検証
