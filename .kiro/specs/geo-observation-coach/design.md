# Design Document

## Overview

Nuxt 4 の単一リポジトリで、フロントエンド（Vue 3 SPA）と API プロキシ（Nitro サーバルート）を完結させる。データベースは使用せず、JSON ファイルで永続化する。

設計上の中心的な決定は「AI に何をさせないか」である。以下の処理は AI を使わずコードで完結させる。

- 見落としの判定
- 回答国の正誤判定
- 失敗モードの分類
- 絞り込み力の算出
- 辞書外の用語 ID の排除

AI に任せるのは 2 つだけである。

- 素人語から用語 ID への正規化
- フィードバック文の生成

**1 プレイあたりの AI 呼び出しは 2 回**（正規化 1 回、フィードバック 1 回）。正規化は 14 スロットをまとめて 1 リクエストで処理する。

### スタック選定

| 領域 | 選定 | 理由 |
|---|---|---|
| フレームワーク | Nuxt 4 | Vue 3 が使え、Nitro のサーバルートで API プロキシが同一リポジトリに収まる。Nuxt 3 は 2026 年 7 月末でサポート終了 |
| 言語 | TypeScript | スロット定義とスキーマを型で固定するため |
| 検証 | Zod | AI 出力の検証に使用。型定義と実行時検証を共有する |
| スタイル | Tailwind CSS | 13 スロット分のフォームを短時間で組むため |
| AI クライアント | `openai` npm パッケージ | さくらの AI Engine は OpenAI 互換。`baseURL` の差し替えのみで利用でき、モデルは文字列で切り替えられる |
| 永続化 | JSON ファイル | 単一利用者、20 問規模。DB は過剰 |
| テスト | Vitest | 採点ロジックはコードで完結するため単体テストが有効 |

## Architecture

```
ブラウザ (Vue 3 SPA)
  │
  ├── iframe ──────────────→ Maps Embed API（画像は保存しない、無料・無制限）
  │
  └── fetch
        │
        ▼
   Nitro サーバルート（API キーはここに閉じる）
        │
        ├── さくらの AI Engine（正規化・フィードバック・辞書生成）
        ├── Street View メタデータ照会（pano ID 有効性確認、無料）
        └── JSON ファイル読み書き（data/）
```

Street View の画像はブラウザ内の iframe にのみ存在し、サーバやリポジトリを通過しない。AI へも送信されない。

## Data Models

```ts
export const SLOT_IDS = [
  'traffic_side', 'road_marking', 'bollard', 'pole', 'sign', 'script',
  'ground', 'terrain_vegetation', 'architecture', 'vehicle',
  'pavement', 'camera', 'season',
  /** 他のどのスロットにも入らない観察の受け皿。辞書を育てる入口として機能する */
  'other',
] as const
export type SlotId = typeof SLOT_IDS[number]

export type SlotState = 'visible' | 'absent' | 'unknown'
export type Confidence = 'high' | 'medium' | 'low'

/** スロット 1 件。教材データと学習者回答で同一の形を使う */
export interface SlotEntry {
  state: SlotState
  /** 素人語の原文。state が visible のときのみ意味を持つ */
  plain: string | null
  /** 正規化された用語 ID。辞書内の ID のみを含む */
  terms: string[]
  /** 教材データでのみ使用。人手確認済みか */
  confirmed?: boolean
}

/** 出題と正解タグ */
export interface Question {
  id: string
  panoId: string
  /** pano ID 失効時の再解決用 */
  fallback: { lat: number; lng: number; heading: number }
  /** ISO 3166-1 alpha-2 */
  country: string
  region: string | null
  difficulty: 1 | 2 | 3
  /** メタデータの著作権表記。Google 提供のもののみ採用する */
  copyright: string
  /** メタデータの撮影年月。管理モードのタグ付け補助にのみ使用し、学習者には表示しない */
  captureDate: string | null
  slots: Record<SlotId, SlotEntry>
  /** 候補を弁別できるスロット。フィードバックで弁別の指示に使う */
  decisiveSlots: SlotId[]
  note: string | null
  source: { draftBy: ('country_table' | 'ai')[] }
}

/** 学習者の回答 */
export interface Answer {
  questionId: string
  slots: Record<SlotId, SlotEntry>
  /** 最大 3 件。high は最大 1 件 */
  candidates: { country: string; confidence: Confidence }[]
  decisiveSlot: SlotId | null
  reasoning: string | null
}

/** 用語辞書の 1 項目 */
export interface Term {
  id: string
  slot: SlotId
  canonical: string
  plain: string
  aliases: string[]
  /** 同一の手がかりを共有する国。件数が絞り込み力になる */
  countries: string[]
  confusableWith: string[]
  note: string | null
  verifiedByHuman: boolean
  /** 生成時にモデル間で不一致があった項目 */
  disputed: boolean
}

export type FailureMode =
  | 'observation_miss'    // 観察漏れ
  | 'knowledge_gap'       // 知識欠落
  | 'discrimination_fail' // 弁別失敗
  | 'confident_error'     // 自信のある誤り
  | 'aware_of_gap'        // 手がかり不足を自覚

export interface GradingResult {
  variant: 'v1' | 'v2'
  /**
   * 名前のない手がかりを自力で見つけた記録。
   * `other` スロットの記述が正解タグの `other` と対応した場合に記録する。
   * 失敗の診断ではなく発見の記録であるため、failureModes とは別に持つ。
   *
   * v1 では正解タグがないため null。
   */
  discoveries: string[] | null
  /** 正解が候補集合に含まれるか。v1 でも算出できる */
  hit: boolean
  /** 含まれる場合、その候補の確信度。v1 でも算出できる */
  hitConfidence: Confidence | null
  /** 以下 3 つは正解タグとの差分計算。v1 では算出できないため null */
  missedSlots: SlotId[] | null
  wrongAbsentSlots: SlotId[] | null
  overclaimedSlots: SlotId[] | null
  /**
   * 失敗モードの分類。v1 では算出できないため null。
   *
   * confident_error と aware_of_gap は正解タグなしでも判定できるが、
   * observation_miss と discrimination_fail は判定できない。
   * 一部だけ埋めた配列を返すと「診断が済んだ」ように見えるため、v1 では
   * 配列全体を null にする。
   */
  failureModes: FailureMode[] | null
  /** 併記された国の組。回答だけから算出でき、v1 でも出せる */
  confusionPairs: [string, string][]
  /** スロット別の絞り込み力（関連国の件数）。辞書が必要。v1 では null */
  narrowingPower: Partial<Record<SlotId, number>> | null
  /**
   * 学習者が挙げた用語の関連国の積集合。実際に達成された絞り込みを表す。
   * 個々には弱いメタでも、積集合は決定的になりうる。
   * 集合演算であり AI を使わずコードで計算する。
   *
   * 辞書が必要なため v1 では null。
   */
  intersection: {
    countries: string[]
    /** 正解国が積集合に含まれているか */
    containsAnswer: boolean
  } | null
  /**
   * 次に見るべきスロット。正解タグと用語辞書から積集合の縮小量を計算して決定する。
   * AI の推測ではなく計算結果である。v1 では正解タグがないため算出できない。
   */
  nextPriority: { slot: SlotId; resultingSize: number }[] | null
  feedback: string
}
```

#### `null` は「判定不能」を表す。空配列とは別である

**v1 で算出できない項目は `null` にする。`[]` にしてはならない。**

`[]` は「計算した結果、該当がなかった」を意味する。`null` は「計算できなかった」を意味する。
この 2 つを混ぜると、v1 の採点が「見落としゼロ」と読める出力になる。**満点に見える誤りが最も悪い。**

これはスロットの状態で `absent`（写っていない）と `unknown`（見ていない）を必ず区別する、
という本アプリの中心的な規約と同じ構造である。**同じ規約を採点結果の型にも適用する。**

真偽値のフラグ（`judgmentUnavailable: boolean`）を別に持たせる案は採らない。
フラグは無視できるが、`null` は TypeScript が分岐を強制する。
**型で防げるものを規律で防がない。**

判定不能を UI に出すときは「判定していない」と明示する。空欄にしない。

## 設計思想

### 鍛える対象は観察と判断の結合である

**本アプリが鍛えるのは、知識でも速度でもなく、「何を見て、どう判断するか」の結合である。**

学習者の表現を借りれば「シナプス連携」を鍛える。観察という入力と、国の判断という出力を結ぶ経路そのものを対象とする。

この定義により、実戦との分業が明確になる。

| | 鍛えるもの |
|---|---|
| **本アプリ** | 観察と判断の結合 |
| **実戦（NoMove 1 分など）** | 速度 |

**速度は実戦で鍛えるべきものであり、本アプリの役割ではない。** 本アプリで経過時間を測ろうとするのは筋違いである（後述）。

### 消費は設計ではなく学習で発生させる

**リクエストの消費が、設計の都合ではなく学習者の行動に比例するようにする。**

そうすると消費が式で書ける。

```
v1 : 1 プレイあたり  1                （採点のみ。辞書がないため正規化しない）
v2 : 1 プレイあたり  1 + モデル数      （正規化 1 回 ＋ モデルごとに採点）
```

**正規化がモデル数に乗らない。** 正規化の出力（用語 ID）はコードが使う事実であり、
モデルに依存しないため 1 回で足りる。**採点だけがモデルごとに増える。**

日常の学習は 1 モデルなので 1 プレイ 2 リクエストである。

| 使い方 | 月の消費 | 月 3,000 に対して |
|---|---|---|
| 毎日 5 プレイ（v2、1 モデル） | 300 | **10%** |
| 10 問 × 4 モデルで v1 を記録 | 40 | 1.3% |
| 10 問 × 4 モデルで v2 と比較 | 50 | 1.7% |

#### 式が書けるのは、以下をすべて AI に投げなかったからである

| 処理 | AI に投げたら | 実際 |
|---|---|---|
| 見落としの検出 | プレイごとに +1 | **コード（集合演算）** |
| 積集合の計算 | プレイごとに +1 | **コード** |
| 絞り込み力の算出 | プレイごとに +1 | **コード** |
| 次に見るべきスロットの算出 | プレイごとに +1 | **コード** |
| 再出題の選定 | セッションごとに +n | **コード** |
| 用語の検索 | クエリごとに +1（RAG） | **プロンプトに同梱**（50 語なら入る） |
| 正解タグの生成 | 出題ごとに +n | **事前生成してファイル化** |
| 画像認識 | 出題ごとに +1 | **やらせない** |

**14 スロットの正規化を 1 リクエストにまとめている**のも同じ理由である。
スロットごとに呼べば 1 プレイ 14 リクエストになる。

#### 読めなくなる設計の型

以下は消費が事前に計算できなくなる。**採らない。**

- **リトライ**（失敗のたびに倍数がかかる。しかも 504 は消費される）
- **自動再採点**（人間が押すボタンにする）
- **エージェント的な多段呼び出し**（AI の判断で次の呼び出しが決まる構造）
- **実行時の RAG 検索**（クエリ数が読めない。無償プランでも課金対象）

**「AI に判断させる回数」を設計に埋め込むと、上限が消える。**
判断はコードがし、解釈だけを AI に渡す。**この責務境界が、消費の見通しと同じものを守っている。**

### 画面の優先順位：コード算出分が主、AI の解釈が従

**本アプリの目的は、学習者が「何を見て、何を言語化すれば国当ての精度が上がるか」を得ることである。**
AI の解釈はその手段の一部であり、全体ではない。**採点とコーチングであって、審判ではない。**

この目的に直接答えるのはコードが計算する部分である。

| | 内容 | 学習者に与えるもの |
|---|---|---|
| **主** | 見落としスロット、絞り込み力、積集合、次に見るべきスロット | **何を見ればよかったか。次にどこを見るか** |
| **従** | `feedback` | 素人語と正規用語の橋渡し、失敗モードの説明 |

**画面のレイアウトはこの順序に従う。** `feedback` を最上部に大きく置かないこと。

理由。コード算出分は**モデルを替えても変わらない**。正解タグと辞書から計算した結果であり、
検証可能である。`feedback` はモデルによって変わる解釈である。
**変わらないものを主に、変わるものを従に置く。**

これは責務境界（確実に判定できるものはコード、曖昧さの解釈だけ AI）を、
画面の情報設計にも適用したものである。

#### 複数モデルの同時採点は既定にしない

複数モデルを並べて表示する機能（タスク 26.1）は、**明示的に選択したときだけ動く副機能とする。
既定は 1 モデルである。**

**学習者の注意が AI の比較に向くと、目的から逸れる。** 風景を観察する訓練のはずが、
AI の出力を観察する時間になる。

同時採点が最も価値を持つのは **v1** である。中身のない励ましが 4 通り並ぶことに意味がある。
v2 ではコード算出分が主役であり、並列表示の必要性は下がる。

### 失敗モードは結合の状態を表す

4 つの失敗モードは、結合のどこが壊れているかの分類として読める。

| 失敗モード | 結合の状態 |
|---|---|
| 観察漏れ | 入力が欠けている |
| 知識欠落 | 結合先が存在しない |
| 弁別失敗 | 結合が曖昧 |
| **自信のある誤り** | **誤った結合が強固** |

**「自信のある誤り」を最優先の修正対象とする根拠がこれである。** 誤った結合が強化されている状態が最も危険であり、放置すると誤りが定着する。

### 解くべき問題は知識ではなく想起である

GeoGuessr のメタ知識は、既に整理された資料が存在する（[Plonk It](https://www.plonkit.net/)）。コミュニティが極めて詳細に curate している。

**したがって本アプリが解く問題は知識の提供ではない。**

最初に定義した 3 つの失敗モードに対して、資料を読むことで解決するのは 1 つだけである。

| 失敗モード | 資料を読むことで解決するか |
|---|---|
| 知識欠落（見えているが意味を知らない） | **解決する** |
| 観察漏れ（写っているのに見ていない） | **解決しない** |
| 想起失敗（知っているが思い出せない） | **解決しない** |

読むという行為は受動的であり、後者 2 つは原理的に解決できない。

そして資料の量が個人の処理能力を超えている。102 カ国分を読み流しても、**頭に散った断片を、風景を前にして引き出せない。**

### スロットは想起の手がかりである

14 スロットの役割は「どこを見ればよいか教える足場」にとどまらない。**より重要な役割は retrieval cue（想起の手がかり）である。**

`bollard` という枠が提示されることで「ボラードについて何か知っていた」という検索が始まる。枠がなければ、知識が頭の中にあっても引き出されない。**断片を引き出すためのインデックスとして機能する。**

3 つの要素が揃って想起の訓練になる。

| 要素 | 役割 |
|---|---|
| 14 スロット | 想起の手がかりを与える |
| 絞り込み力 | その手がかりがどれだけ効くかを教える |
| 素人語の正規化 | 「気づいたが名前を知らない」を橋渡しする |

### 知識が増えると想起が遅くなる

学習者の実感として、**資料を読み込むほど弱くなる**という現象が報告されている（最高到達 Master 4、現在 Gold 1）。

考えられる機構は以下である。断定はしないが、設計上はこれを前提とする。

1. 知識が増えると候補集合が広がる
2. 候補が多いほど探索に時間がかかる
3. GeoGuessr は時間制限があり、対戦相手と競う
4. 収束する前に置かざるを得ず、相手より悪い場所に置いて負ける

**したがって知識量の増加が、時間制約下では性能低下につながりうる。**

### 用語は GeoGuessr コミュニティの語彙に合わせる

**本設計で「絞り込み力」と呼んでいる概念は、GeoGuessr コミュニティでは「強いメタ／弱いメタ」と呼ばれている。**

**内部の数値としては `narrowingPower`（該当国数）を保持するが、UI 表示は「強いメタ／弱いメタ」に統一する。** 対象利用者が GeoGuessr プレイヤーであるため、既存の語彙を使う。

独自の用語を作ってはならない。**既に人間が名前を付けているものに別の名前を与えるのは、本プロジェクトの主題と矛盾する。**

### メタの強さは 2 軸で決まる

**該当国数だけでは判定できない。地理的な散らばりも効く。**

GeoGuessr の失点は距離で決まる。同じ 3 カ国でも、隣接していれば失点が小さく、大陸が違えば失点が大きい。したがって「3 カ国に絞れた」という事実だけでは、そのメタの価値が決まらない。

GeoGuessr プレイヤーの区分に合わせる。

| 区分 | 条件 |
|---|---|
| **最強メタ** | 1 カ国に確定（本来はリージョンまで絞れるものを指すが、本アプリは国レベルまで） |
| **強メタ** | 2 カ国に絞れ、かつ地理的に近い |
| **良メタ** | 3〜4 カ国、**かつ地理的に近い**（失点が小さい） |
| **補助メタ** | 5 カ国以上、または**大陸をまたぐ**。主役になれず、組み合わせ用 |

**3〜4 カ国でも大陸が違えば良メタではない。** 単独では判断の主役になれず、他と組み合わせるべき補助的なメタである。

#### 判定アルゴリズム

候補国の集合 `C` に対して、`regions.json` の地域・大陸グループを引いて判定する。

```
size = |C|
sameRegion    = C の全要素が同一の地域グループに属する
sameContinent = C の全要素が同一の大陸グループに属する

size == 1                        → 最強メタ
size == 2 かつ sameRegion        → 強メタ
size <= 4 かつ sameRegion        → 良メタ
size <= 4 かつ sameContinent     → 良メタ（やや弱い）
それ以外                          → 補助メタ
```

該当国数と散らばりを併記する（「補助メタ（8 カ国、2 地域にまたがる）」のように）。

#### 実例

| メタ | 件数 | 散らばり | 区分 |
|---|---|---|---|
| かな漢字 | 1 | — | 最強メタ |
| 繁体字 | 2（HK TW） | 同一地域 | 強メタ |
| キリル文字 | 8 | 東欧 + 旧ソ連の 2 地域 | 補助メタ |
| **スペイン語** | 15 | **ヨーロッパ + 北中米 + 南米、2 大陸** | 補助メタ（最も弱い） |

**スペイン語がキリル文字より弱いのは、件数だけでなく大陸をまたぐためである。** 外したときの失点が桁違いになる。

#### 対象外：リージョン絞り込み

プレイヤーの本来の定義では、最強メタは「1 カ国に確定し、さらに国内のリージョンまで絞れる」ものを指す。Plonk It のカザフスタンの電柱の塗装（8 地域分）がその例である。

**本アプリは国レベルまでを対象とし、リージョン絞り込みは扱わない。** 用語辞書の関連国が国コードのみであるため、構造的に対応していない。この限界は記事に明記する。

### 組み合わせの絞り込みは積集合で計算する

**実際のスキルは、単独の手がかりの強さを知ることではなく、組み合わせて絞ることである。**

```
キリル文字        → 8 カ国（RU UA BG RS MK KZ KG MN）
EU 式ナンバープレート → 27 カ国
────────────────────────────────────────
積集合            → ブルガリア 1 カ国
```

**個々には弱いメタでも、積集合は決定的になる。** したがって「弱いから軽視する」のは誤りである。弱いメタは組み合わせの材料として必要である。

学習者が挙げた用語の関連国の**積集合のサイズが、実際に達成された絞り込みを表す。** これは集合演算であり、**AI を使わずコードで計算できる。**

`GradingResult` に以下を保持する。

- 学習者が挙げた用語から計算した積集合と、そのサイズ
- 正解国が積集合に含まれているか
- 積集合を 1 カ国にできた組み合わせが存在したか

### 次に見るべきスロットはコードで計算できる

**`nextPriority` を AI から コードへ移す。**

正解タグがあれば、未観察のスロットについて「そこを見たら積集合がどこまで縮むか」を正確に計算できる。

```
現在の積集合 = 8 カ国（キリル文字のみ）

未観察スロットごとに、正解タグの用語で積集合を取る:
  vehicle    → 1 カ国   ← これを見れば確定する
  bollard    → 3 カ国
  pole       → 5 カ国
  season     → 8 カ国   ← 見ても絞れない
```

**AI に推測させる必要がなく、しかも AI より正確である。** 正解タグと用語辞書から一意に決まる。

これにより責務境界がさらに移動する。AI に残るのは、この計算結果を学習者にとって意味のある言葉に変える部分だけである。

### 上級者は積集合を暗記している

学習者の観察によれば、**上級者は積集合をリアルタイムで計算しているのではなく、組み合わせをひとつの塊として記憶している。**

「キリル文字 + EU 式ナンバー = ブルガリア」は、計算されるのではなく想起される。

習熟段階との対応。

| 段階 | やっていること |
|---|---|
| 初級 | 個々のメタを覚える |
| **中級** | **組み合わせを覚える。組み合わせ爆発するため最も負荷が高い** |
| 上級 | 組み合わせが自動化されている |

**中級の壁は組み合わせの数である。** どの組み合わせを覚えるべきか分からないまま総当たりで蓄積するしかない。

### 覚える価値のある組み合わせは計算で抽出できる

本アプリはこの壁に対して直接効く。**上級者が何年もかけて蓄積した塊を、計算で導出して提示できる。**

用語辞書だけで計算でき、プレイデータは不要である。

#### 抽出条件

**件数の閾値ではなく、メタの区分で判定する。**

```
どちらの用語も単独では最強メタでない（1 カ国に確定しない）
かつ
積集合が良メタ以上（最強メタ・強メタ・良メタ）
かつ
積集合が両方の単独より真に小さい（情報が増えている）
```

**単独で 1 カ国に確定する用語は、組み合わせても情報が増えない**ため除外する。それ以外は、片方が既に強メタであっても抽出対象とする。「最後の 1 ピース」型の組み合わせを拾うためである。

積集合の判定にも地理的な散らばりを用いる。**積集合が 3 カ国でも大陸をまたぐなら、覚える価値は低い。**

#### 代表例：左側通行

**単独では最も弱く、組み合わせでは最も効くメタ。**

```
左側通行 → 24 カ国 / 8 地域 / 4 大陸
  ヨーロッパ : GB IE MT CY
  アフリカ   : KE UG NA BW ZA LS SZ
  アジア     : IN LK BD NP BT TH MY SG ID HK JP
  オセアニア : AU NZ
```

**初心者でも一目で判別できるのに、単独では何も絞れない。** 4 大陸にまたがるため、これだけで回答すれば失点が最大になる。

しかし最後の 1 ピースとして機能する。

```
繁体字      → 2 カ国（HK TW）    強メタだが確定しない
左側通行    → 24 カ国            単独では無価値
────────────────────────────────────────
積集合      → 香港 1 カ国確定
```

この例は抽出条件の設計に影響した。「両方が補助メタ」という条件では繁体字（強メタ）が除外され、**この組み合わせを拾えなかった。** 条件を「どちらも最強メタでない」に緩めた理由である。

用語 200 語なら約 2 万ペア。総当たりで計算できる。

3 つ以上の組み合わせは組み合わせ数が爆発し、かつノイズが増えるため、まずはペアのみを対象とする。

#### 出力形式

インタラクティブな UI は不要である。スクリプトで Markdown の学習リストを生成する。実装コストが低く、記事の成果物としても提示できる。

#### v1 ではこの計算ができない

`v1` は正解タグを持たないため、積集合の縮小量を計算できない。優先順位は AI の推測に頼るしかなく、精度が落ちる。

**これは v1 と v2 の対比を 1 つ増やす。** 同じ画面、同じプロンプト骨格でありながら、v2 では計算に基づく正確な優先順位が出て、v1 では推測が出る。

### 絞り込み力の本質は探索順序である

上記の帰結として、絞り込み力の意味づけを変える。

| 従来の解釈 | 改訂後の解釈 |
|---|---|
| この手がかりは何カ国に絞れるか | **どの順序で手がかりを探すべきか** |

弱いメタ（ラテン文字、該当 71 カ国）を最初に確認するのは時間の無駄である。強いメタを先に探すべきである。**網羅性の問題ではなく探索順序の問題である。**

これは GeoGuessr プレイヤーの間で「**強いメタを優先する**」として既に共有されている原則である。本アプリはその原則を、該当国数という数値で裏付けて提示する。

`GradingResult.feedback` の `nextPriority` は、この観点で優先順位を提示する。「見落としを埋める」ためではなく「強いメタから順に探す」ためである。

### 時間は測らない

想起速度が問題であるならば時間を測るべきだと考えたが、**本アプリでは測れない。**

このアプリの経過時間が測るのは、タイピング速度と記述量である。観察が改善して記述が増えれば時間は伸びる。**指標が目的と逆を向く。**

さらに本アプリは意図的に遅い設計である。じっくり言語化させることが目的であり、速度を競う場ではない。実戦の想起速度（見て、気づいて、置く）とは性質が異なる。

**速度は実戦で鍛え、実戦で測る。** NoMove の時間制限モードなどが適している。本アプリは観察と判断の結合を鍛える役割に限定する。この分業は記事に明記する。

### 探索順序の質は測れる

時間を測らずに、時間効率に直結するスキルを測る方法がある。

**決め手にしたスロットの絞り込み力である。**

学習者は毎回「一番の決め手にした項目」を 1 つ選ぶ（`Answer.decisiveSlot`）。その選択の質は、選んだスロットの絞り込み力で評価できる。

| 選んだ決め手 | 評価 |
|---|---|
| 絞り込み力 71 の手がかり（ラテン文字） | 優先順位付けが不適切 |
| 絞り込み力 1〜2 の手がかり | 適切 |

10 プレイを通して、決め手に選ぶスロットの絞り込み力が下がっていけば、**探索順序の判断が改善している**ことを示す。これが実戦の速度に直結するスキルである。

`decisiveSlot` と `narrowingPower` は既に保持しているため、追加の実装は不要である。

### 情報が提示されるタイミングが異なる

資料は**事前に読む**ものである。本アプリは**観察して間違えた直後に、該当する情報が出る**ものである。

同じ情報でも提示の順序が逆である。一般に後者の方が定着すると言われるが、本プロジェクトで測定したわけではないため断定はしない。

### 観察空間は無限であり、スキーマには穴がある

GeoGuessr は Street View 上のあらゆる情報を用いて場所を推測するゲームであり、**観察空間は原理的に無限である。** 14 スロットはその有限な切り出しにすぎない。

ルワンダの例（ゴミが落ちていない）でスキーマの穴が判明したのは偶然ではなく、**原理的に必ず起こることである。**

この帰結として、**本アプリには天井がある。** スキーマの外を見ている上級者に対しては何も返せない。対象は初級から中級までである。この限界は隠さず記述する。

### AI の役割：人間が気づいたものに名前を与える

気づくのは人間である。人間の視覚と対比の能力は、パターンに名前がついていなくても差異を検出する。AI にできるのは、気づかれたものに語彙を与え、既知の手がかりに接続し、絞り込み力を定量化することである。

| 担い手 | 役割 |
|---|---|
| 人間 | 見る。パターンに気づく（**名前のないものも含めて**） |
| AI | 名前を与える。既知のメタに接続する。絞り込み力を示す |
| コード | 検証可能なものを判定する |

「A の上に丸」を `Å` に翻訳する処理が、この構造の典型である。**気づきは人間側にあり、AI は語彙を貸すだけである。**

### `other` は最高信号として扱う

`other` スロットの記述は、正規化の観点では常に「該当なし」となる。しかしそれは価値がないという意味ではない。

学習者の `other` の記述が正解タグの `other` と対応した場合、それは**名前のない手がかりを自力で見つけた**ことを意味する。失敗の診断ではなく**発見の記録**として扱い、`GradingResult.discoveries` に保持する。

`other` の記述は同時に辞書追加候補として最優先で蓄積する。学習者が名前のないものを見つけた記録が、そのまま辞書を育てる。

## Components and Interfaces

### 画面構成と状態遷移

3 ページのみ。ルーティングは Nuxt のファイルベースに従う。

#### 学習モード（`/`）

```
出題読み込み
  → pano ID 検証（失敗時は座標から再解決、それも失敗ならスキップ）
  → 観察フェーズ（iframe + SlotForm）
  → 回答フェーズ（AnswerPanel：候補 3 件 + 確信度 + 決め手スロット）
  → 採点中（正規化 → コード判定 → フィードバック生成）
  → 結果表示（ResultPanel）
  → 次の問題へ
```

`SlotForm` は 13 スロットを縦に並べる。各スロットは 3 状態のトグルと自由記述欄を持つ。`visible` 以外では記述欄を無効化する。ラベルは平易表現を主とし正規用語を括弧で併記し、プレースホルダに入力例を表示する。

#### 管理モード（`/admin`）

学習モードと **同一の `SlotForm` コンポーネント** を `mode="admin"` で使う。差分は以下のみ。

- 下書きを表示する（グレー表示で未確認を示す）
- スロットごとに「確認済み」トグルを持つ
- 全スロットが確認済みまたはクリアされるまで保存ボタンを無効化する
- 一括承認ボタンは実装しない
- `decisiveSlots` と `difficulty` の入力を必須とする

#### 用語集（`/glossary`）

`glossary.json` を一覧表示する。絞り込み力（関連国の件数）を併記し、件数が少ない用語を強い手がかりとして上位に表示する。

### サーバ API

| エンドポイント | 用途 | AI 使用 |
|---|---|---|
| `GET /api/questions` | 出題の取得 | なし |
| `POST /api/questions` | 教材データの保存 | なし |
| `GET /api/pano-validate` | pano ID の有効性確認 | なし |
| `POST /api/normalize` | 素人語 → 用語 ID | あり |
| `POST /api/grade` | 採点とフィードバック | あり |
| `POST /api/draft` | タグ下書き生成 | あり |

### 採点パイプライン

処理順と担い手を固定する。この順序が「AI に何をさせないか」の実装である。

| 順 | 処理 | 担い手 | 備考 |
|---|---|---|---|
| 1 | 回答の受領と検証 | コード | Zod |
| 2 | 素人語の正規化 | **AI** | 14 スロットを 1 リクエストで一括処理。`other` は常に「該当なし」となる |
| 3 | 辞書外 ID の排除 | コード | AI の遵守に依存しない |
| 4 | 見落とし判定 | コード | 正解タグとの差分 |
| 5 | 回答国の判定 | コード | 候補集合への包含と確信度 |
| 6 | 失敗モードの分類 | コード | 下記の判定表 |
| 7 | 絞り込み力の算出 | コード | 辞書の `countries` の件数 |
| 8 | **積集合の算出** | コード | 挙げた用語の `countries` の積集合。集合演算 |
| 9 | **次に見るべきスロットの算出** | コード | 正解タグと辞書から縮小量を計算。v1 では算出不能 |
| 10 | フィードバック生成 | **AI** | 4〜9 の結果を入力として渡す |
| 11 | 記録 | コード | `data/runs/` へ保存 |

#### 失敗モードの判定表

コードで決定的に判定する。複数該当しうるため配列で保持する。

| 条件 | 判定 |
|---|---|
| 正解タグにある手がかりが `unknown` | `observation_miss` |
| 正解が候補集合に含まれず、最高確信度が `high` | `confident_error`（最優先で提示） |
| 正解が候補集合に含まれ、確信度が `medium` または `low` | `discrimination_fail` |
| 正解が候補集合に含まれず、全候補が `low` | `aware_of_gap` |
| スロット記述が正確かつ正解が候補集合に含まれない | `knowledge_gap` |

#### フィードバック生成の入力

AI に渡すのは以下のみ。**Street View の画像は渡さない。**

- 学習者のスロット記述（原文と正規化後の用語 ID）
- 正解タグ（`v2` のみ）
- 該当する用語辞書の抜粋（`v2` のみ）
- コードで確定した判定結果（見落とし、正誤、失敗モード、絞り込み力）
- 正解国と地域

プロンプトで以下を制約する。

- 正解タグに記載された手がかりのみ「この地点に写っている」と断定してよい
- 辞書由来の知識は「この国では一般に」という一般論として述べる
- 弁別スロットを明示し、次に見るべき優先順位を提示する

### v1 / v2 の切り替え

同一のエンドポイント、同一のプロンプトテンプレートを使い、**渡す情報だけを変える**。

```ts
// grade.post.ts
const variant = body.variant // 'v1' | 'v2'

const context = variant === 'v2'
  ? { answerKey: question.slots, glossary: relevantTerms }
  : { answerKey: null, glossary: null }
```

`v1` では以下が成立する。

- 正解タグを参照しないため、見落とし判定は「判定不能」を返す
- 辞書を参照しないため、正規化は行わず素人語のまま AI に渡る
- フィードバックは国の一般知識のみに基づく

プロンプトの骨格を共有することが要件 9-3 の条件である。テンプレートを分岐させず、差し込むコンテキストの有無だけで切り替える。

### ストリーミングの扱い

**採点の応答は `gpt-oss-120b` で 22〜27 秒を要する。** 何も表示されない画面を 25 秒見せるのは学習ツールとして成立しない。

一方、**構造化出力とストリーミングは相性が悪い。** JSON を途中まで受信してもレンダリングできる要素がなく、部分 JSON のパースは壊れやすい。

したがって以下の方針とする。

- **ストリーミングで受信するが、用途は進捗表示に限る。** 推論フィールドの流入を「処理中」の根拠として使う
- **JSON が完成してから結果をレンダリングする**
- **`finish_reason` の有無を必ず検証する。** 返っていない場合は打ち切られており、失敗として扱う

これにより体感速度を改善しつつ、構造化出力の利点（UI 描画の安定、モデル比較における機械的な突き合わせ）を保持する。

#### 実測（2026-08-07、`preview/Kimi-K2.6`、6 カ国のバッチ）

| 項目 | 値 |
|---|---|
| ヘッダ受信 | **1,180 ms** |
| 最初のチャンク | **1,181 ms** |
| 全体 | 94,195 ms |
| チャンク数 | 4,389 |
| `finish_reason` | `stop` |
| 件数 | 6/6 |

**初バイトが 1.2 秒で到達する。** 非ストリーミングでは同じ処理で 94 秒間何も返らない。採点に 20〜30 秒を要する本アプリにおいて、この差は決定的である。

**推論フィールドもストリーミングされる。** `delta.reasoning` で 5,132 字を受信した。進捗表示の根拠として使えることが確認できた。

#### ストリーミングでもタイムアウトは回避できない（検証済み）

30 カ国を一度に投げて 300 秒を超える実行を作り、検証した。

| 項目 | 値 |
|---|---|
| HTTP | 200 |
| ヘッダ受信 | 3,347 ms |
| 全体 | **305,182 ms** |
| チャンク数 | 17,759 |
| `content` | **0 字** |
| `reasoning` | 22,458 字 |
| `finish_reason` | **なし** |

**約 305 秒でストリームが打ち切られた。** 推論のみを出力した状態で接続が閉じられ、本文に到達していない。

非ストリーミングの 504 が 300,649 ms、ストリーミングの打ち切りが 305,182 ms。いずれも約 300 秒であり、**タイムアウトは総所要時間に対する制限である。ストリーミングでは回避できない。**

#### 失敗の仕方はストリーミングの方が悪い

| 方式 | 応答 | 検出可能性 |
|---|---|---|
| 非ストリーミング | HTTP 504 + エラー本文 | **明示的に失敗が分かる** |
| ストリーミング | HTTP 200 + `finish_reason` なし + 本文 0 字 | **成功に見える** |

構造化出力の件数欠損と同じ構造である。**HTTP 200 は成功を意味しない。**

**ストリーミングを使う場合、`finish_reason` の有無を必ず検証すること。** 所要時間やチャンク数で成否を判断してはならない。17,759 個のチャンクが届いていても、生成は完了していない。

#### 結論

ストリーミングの採用理由は**体感速度の改善のみ**である。タイムアウト対策にはならない。

タイムアウトへの対処は、**1 リクエストあたりの処理量を小さく保つこと**に限られる。30 カ国を一度に投げれば失敗し、6 カ国なら通る。バルク処理はバッチを小さく分割する。

### エラー種別による消費の違い

**実測（2026-08-07）。エラーの種類によってリクエスト数の消費が異なる。**

| エラー | 消費 | 理由 |
|---|---|---|
| HTTP 400（パラメータ誤り） | **されない** | 検証段階で弾かれ、推論が走らない |
| HTTP 504（タイムアウト） | **される** | 推論は走ったが応答が返らなかった |

根拠。仕様書生成では 18 回試行のうち 3 回が 400 で失敗し、カウントは 15 だった。国定数テーブルの生成では 68 回試行のうち 1 回が 504 で失敗したが、カウントは 68 増えた。

**この違いはリトライ方針に直結する。** 504 でリトライすると、成功する保証がないまま枠を消費する。したがって**リトライは実装しない。**

失敗は事実として記録する。リトライで通してしまうと「このモデルはこの用途では完走しない」という構造的な制約が記録から消える。

| モデル | 誤答 | 応答時間 | 備考 |
|---|---|---|---|
| `preview/Kimi-K2.6` | **0 / 9** | 54〜300 秒超 | 最遅。504 も発生。件数欠損も起こした |

採点用に選定した `gpt-oss-120b` はオーストラリアの走行車線を誤答した。左側通行は基本的な事実である。**「出力が充実している」ことは「正確である」ことを意味しない。**

この結果は用途ごとのモデル選定を裏付ける。速度が要る処理（正規化）と精度が要る処理（事実の生成）で、選ぶべきモデルが異なる。

### enum にしないフィールドは突き合わせできない

| フィールド | 形式 | 突き合わせ |
|---|---|---|
| `traffic_side` | enum（2 値） | **成立**。完全一致で比較できた |
| `scripts` | enum（20 値） | **成立**。集合として比較できた |
| `languages` | 自由記述 | **不成立**。表記揺れで比較不能 |

`languages` の実測。

```
同一言語の表記揺れ  : chinese / 中国語(繁体字) / 繁体字中国語 / 中国語（広東語）
                      fr / フランス語 / フランス語 (french)
フィールドの取り違え: MG に「右側通行」「白地に黒文字。上部に MADAGASCAR ...」
                      PR に「puerto rico」「走行側：右側通行」
```

単純な和集合ではフィールドの取り違えが混入する。2 モデル以上の一致を要求する閾値を設けると、表記揺れによって正しい言語まで落ちた（香港で中国語が消え、マダガスカルは全滅した）。

**プロンプトで「英語の小文字表記」と指示したが守られなかった。指示ではなくスキーマで縛る必要がある。**

`languages` は採用値を作らず、モデル別の生の出力を `languages_by_model` に保持するのみとする。`script` スロットの下書きには enum で揃った `scripts` を使い、絞り込み力の計算には用語辞書の `countries` を使うため、実害はない。

### 人手訂正の仕組み

多数決が誤るため、訂正を明示的に管理する。`countries-overrides.json` に以下を記録する。

- 対象の国とフィールド
- 変更前と変更後の値
- **根拠（`reason`）**。後から検証できない訂正を入れない
- `status`。`confirmed` のものだけを適用し、`proposed` は適用しない

適用した国は `verifiedByHuman` を `true` にし、`overrideReason` に根拠を残す。

## Error Handling

### 構造化出力

**検証済み（2026-08-07、`gpt-oss-120b`）。`json_schema` の `strict: true` が動作する。**

出力に文法制約デコーディングの痕跡が見られ、プロンプトによる依頼ではなくデコード段階でスキーマが強制されていると判断できる。`json_object` も動作する。

したがって主経路は `json_schema` + `strict: true` とする。フォールバックは以下の順で維持する。

1. `response_format: { type: 'json_schema', strict: true, ... }` ← 主経路
2. `response_format: { type: 'json_object' }`
3. プロンプトによる JSON 指示のみ

いずれの経路でも **Zod による検証をコード側で必ず実施する**。要件 3-2（辞書外の用語を生成しない）を AI の遵守に依存させない。

#### enum による用語 ID の制約

正規化のスキーマでは、用語 ID を辞書から生成した **enum で制約する**。これにより辞書外の ID は生成不可能となり、要件 3-2 がデコード段階とコード検証の二重で担保される。

**enum には「該当なし」を表す値を必ず含めること。** enum で制約すると、モデルは列挙された値のいずれかを必ず選択する。エスケープハッチがない場合、該当する用語が存在しない入力に対して**誤った ID を強制的に選ばせることになる**。制約が逆にハルシネーションを生む。

```jsonc
{
  "type": "string",
  "enum": ["a_ring", "a_umlaut", "cedilla", /* ... 辞書の全 ID ... */, "none"]
}
```

`"none"` が返された場合は辞書追加候補として記録する（要件 3-3、3-4）。

#### strict が保証する範囲

`strict: true` が保証するのは**構造のみ**である。

- 保証される：出力が enum で指定した値のいずれかであること
- 保証されない：選ばれた値が意味的に正しいこと
- **保証されない：配列の件数や網羅性**

**実測（2026-08-07、国定数テーブルの生成）。** 6 カ国を要求したバッチに対し、以下が発生した。

| モデル | バッチ | 結果 |
|---|---|---|
| `preview/Kimi-K2.6` | 07 | `countries` が **0 件** |
| `preview/Kimi-K2.6` | 11 | 1 件 |
| `preview/Kimi-K2.6` | 15 | 1 件 |
| `preview/Qwen3.6-35B-A3B` | 14 | 1 件 |
| `preview/Qwen3.6-35B-A3B` | 15 | 2 件 |
| `preview/Qwen3.6-35B-A3B` | 17 | `finish_reason=length` で打ち切られ JSON が壊れた |

**失われたデータは 31 / 408（7.6%）。エラーは一切返っていない。** HTTP は 200、`finish_reason` は `stop`、JSON パースも成功している。ログを確認しなければ、欠損したままマージされていた。

**構造化出力を「これで安全」と考えて件数の検証を省くと、静かなデータ欠損が入る。**

#### `minItems` / `maxItems` の効果（実測）

**スキーマに `minItems` / `maxItems` を追加して同じ 6 バッチを再取得した結果、6 件すべてが正しい件数で返った。**

| モデル | バッチ | 追加前 | 追加後 | 所要 |
|---|---|---|---|---|
| `preview/Kimi-K2.6` | 07 | **0/6** | 6/6 | 76.0 秒 |
| `preview/Kimi-K2.6` | 11 | 1/6 | 6/6 | 121.5 秒 |
| `preview/Kimi-K2.6` | 15 | 1/6 | 6/6 | 89.6 秒 |
| `preview/Qwen3.6-35B-A3B` | 14 | 1/6 | 6/6 | 25.2 秒 |
| `preview/Qwen3.6-35B-A3B` | 15 | 2/6 | 6/6 | 16.6 秒 |
| `preview/Qwen3.6-35B-A3B` | 17 | パース失敗 | 6/6 | 19.6 秒 |

**交絡についての注記。** `Qwen3.6-35B-A3B` の batch17 は `max_tokens` も 8,000 から 16,000 に変更しているため、`minItems` 単独の効果とは言えない。一方 batch14 と batch15 は前回も `finish_reason=stop` でありトークン上限に達していなかったため、**この 2 件は `minItems` 追加のみによる改善である。**

**機構は不明である。** `minItems` が制約デコーディング側で強制されたのか、スキーマ記述がプロンプトとして解釈されて効いただけなのかは区別できていない。結果は同じだが、断定はしない。

#### 対処

1. **スキーマに `minItems` / `maxItems` を必ず指定する。** 実測で件数欠損が解消した
2. **コード側でも件数を検証する。** `minItems` の機構が不明であり、保証には依存できない。要求した件数と一致しない応答は不完全として扱い、再取得の対象とする
3. 打ち切り（`finish_reason=length`）はモデルごとに `max_tokens` を調整する

意味の正しさは依然として保証できないため、辞書の人手検証（要件 8-6）と「該当なし」の許容も引き続き必要である。

#### トークン消費の実測

| 経路 | prompt | completion | 内訳 |
|---|---|---|---|
| `json_schema` | 80 | 133 | JSON 約 20 + 推論 約 110 |
| `json_object` | 96 | 219 | JSON 約 20 + 推論 約 200 |

**推論が JSON 本体の 5〜10 倍を消費する。** 13 スロット × enum 50 件では推論がさらに伸びるため、`max_tokens` は 4,000 以上とする。

```
AI 出力 → Zod 検証 → 辞書に存在しない ID を破棄 → 空なら「該当なし」
検証失敗時は 1 回だけ再試行。再失敗時は「該当なし」として処理を継続する
```

「該当なし」となった記述は辞書追加候補として `data/` に追記する。

### その他の異常系

| 事象 | 処理 |
|---|---|
| pano ID が失効 | `fallback` の座標から再解決。失敗時はその出題をスキップし失効を記録 |
| 著作権表記が Google 以外 | 出題候補として採用せず、理由を記録して除外（外部投稿のパノラマは権利者が投稿者のため） |
| AI が応答しない・タイムアウト | 1 回再試行。再失敗時はコード判定の結果のみを表示し、フィードバックは欠落として明示 |
| 正解タグが存在しない出題 | 見落とし判定を実行せず「判定不能」を明示（要件 4-5） |
| 辞書が空 | 正規化をスキップし素人語のまま扱う（v1 相当の動作） |
| リクエスト上限到達 | エラーを画面に表示し、計測ログに記録して停止 |

AI の失敗でアプリ全体が停止しないこと。コードによる判定結果は AI に依存しないため、AI が落ちても見落とし判定と正誤判定は表示できる。

## Testing Strategy

Vitest による単体テストを、コードで完結する処理に集中させる。AI 呼び出しはモックする。

## さくらの AI Engine の接続情報

### エンドポイント

```
https://api.ai.sakura.ad.jp/v1/chat/completions
```

`openai` パッケージの `baseURL` には `https://api.ai.sakura.ad.jp/v1` を設定する。

### アカウントトークンの形式

トークンは `<UUID>:<シークレット>` のペアである。**この形式のまま** `Authorization: Bearer <UUID>:<シークレット>` として送信する。UUID とシークレットを分離してはならない。

トークンは発行時に一度しか表示されない。

### 無償枠

| 区分 | 上限 |
|---|---|
| チャット補完 (chat completions) | 毎月 3,000 リクエスト |
| ベクトル埋め込み (embeddings) | 毎月 10,000 リクエスト |
| 音声の文字起こし (audio transcriptions) | 毎月 50 リクエスト |
| 音声合成 (audio speech) | 毎月 50 リクエスト |

**無償枠はリクエスト数で数えられ、トークン単価は無償枠内では影響しない。** したがってモデル選定において単価を考慮する必要はなく、最上位のモデルを使用する。

**超過時は課金ではなくレートリミットがかかる。** 金銭的なリスクはないが、枠を使い切ると作業が停止する。8/17〜8/19 の追い込み期間に枠切れすると致命的であるため、予算管理を厳守する。

| `llm-jp-3.1-8x13b-instruct4` | — | — | — | **コンテキスト長 4,096 トークン。HTTP 400** |

この実測から得られた判断は以下の 3 点である。

**`llm-jp-3.1-8x13b-instruct4` は本アプリでは使用できない。** コンテキスト長が 4,096 トークンしかなく、採点プロンプト（正解タグ + 用語辞書の抜粋 + 判定結果）や 13 スロット × enum 50 件の正規化スキーマが収まらない。

**`preview/Kimi-K2.6` は採点には使用しない。** 応答に 90〜110 秒を要する。学習ツールとして 1 プレイごとに 2 分待たせる設計は成立しない。無償枠がリクエスト数で数えられるため単価は無関係だが、**応答速度は無関係ではなかった。**

**さらに `preview/Kimi-K2.6` は完了しないことがある。** 国定数テーブルの生成で `504 Request timed out` が発生した。

**タイムアウトは約 300 秒（実測）。**

| 事象 | 所要時間 |
|---|---|
| 504 で失敗した回 | **300,649 ms** |
| 成功した回の最長 | 176,905 ms |
| 成功した回の最短 | 54,567 ms |
| 同じバッチを再実行して成功 | 122,102 ms |

同一のバッチで 54 秒から 300 秒超まで揺れる。**推論時間の変動が大きく、たまに 300 秒を超えて弾かれる。** 300 秒は一般的なタイムアウト値であり、公開されていないが実測と整合する。

つまり「遅いので待つ」という話ではなく、**待っても返ってこないことがある。** バルク処理に使えない。

**タイムアウト値は公開されておらず、変更する手段も提供されていない。** また[サービス基本情報](https://manual.sakura.ad.jp/cloud/ai-engine/01-basics.html)に「品質保証（SLA）の適用対象外です」と明記されており、応答そのものが保証されていない。

対処は以下とする。

- **リトライしない。** 504 はリクエスト数を消費するため、成功の保証がないまま枠を減らす。失敗は事実として記録する
- 欠落したバッチは 3 モデルの合意で進める（`merge-country-table.mjs` は欠落モデルをスキップし `modelCount` に記録するため、設計上許容されている）
- **用語辞書の生成では最初から使用しない。** 辞書生成のプロンプトは 102 カ国の enum を含むため国定数テーブルより重く、タイムアウトの頻度が上がる。代替として `preview/Qwen3-VL-30B-A3B-Instruct` を使う
- ストリーミングで回避できるかを `test-streaming.mjs` で検証する

小型・低単価のモデルが速いとは限らない。`preview/Qwen3-0.6B-cpu` は CPU 実行のため `gpt-oss-120b` より遅い。

### モデル選定

| 用途 | モデル | 選定理由 |
|---|---|---|
| コーディングエージェント | `preview/Kimi-K2.7-Code` | 唯一のコーディング向け |
| 正規化 | `preview/gemma-4-31B-it` | 最速。推論を返さないため無駄が少ない |
| 採点・フィードバック（本番） | `gpt-oss-120b` | 出力の充実度と応答時間（22〜27 秒）の釣り合い |

正規化は 1 プレイごとに走るため速度を優先する。採点は内容の質を優先する。実装後に体感で調整する。

比較対象の 5 モデル（要件 13・14 で共用）。系統とサイズの幅を確保する。

- `gpt-oss-120b` — 標準、reasoning 系
- `preview/Kimi-K2.6` — 最上位（`max_tokens` を 24,000 に設定する）
- `preview/gemma-4-31B-it` — 中位、別系統、reasoning なし
- `llm-jp-3.1-8x13b-instruct4` — 国産（`max_tokens` を 3,500 以下に設定する）
- `preview/Qwen3-0.6B-cpu` — 比較の下限として意図的に含める

`max_tokens` はモデルごとに設定する。一律の値では上記 2 モデルが失敗する。

### 出力の打ち切りと検証の妥当性

`finish_reason` が `length` の場合、**その出力は要件 14 の評価に使用できない。** 規約への言及が打ち切られた部分に含まれていた可能性を排除できないためである。

打ち切られた出力は破棄し、`max_tokens` を上げて再取得する。

**提供終了しているモデルを指定しないこと。** `Qwen3-Coder-30B-A3B-Instruct`、`Qwen3-Coder-480B-A35B-Instruct-FP8`、`preview/Phi-4-multimodal-instruct` は提供終了である。過去の記事や資料にはこれらの名前が残っているため注意する。

「要申請」ステータスのモデルは個人アカウントでは利用できない。

### `reasoning` フィールドへの注意

`gpt-oss-120b` などの reasoning 系モデルは、レスポンスの `message` に `content` とは別に推論内容を返す。

**フィールド名は `reasoning` である。** マニュアルの記載例は `reasoning_content` となっているが、実測（2026-08-07、`gpt-oss-120b`）では `reasoning` が返る。実測を採用する。パース処理では両方のキーを許容する実装とする。

期待する出力は `content` に入る。実測では `content` に回答のみが入り、推論は分離されていた。ただし `content` が空または不正な場合はフォールバックの再試行対象とする。

### `max_tokens` の設定

**`max_tokens` は `reasoning` の消費分を含む。** 実測では「ひとことだけ返してください」という指示に対し、`content` が 4 文字であるにもかかわらず `completion_tokens` が 87 であった。差分は全て推論に消費されている。

構造化出力を要求する処理（正規化、採点）で `max_tokens` を絞ると、推論で枠を使い切って `content` が空になる、あるいは JSON が途中で切れる。

無償枠はリクエスト数で数えられるため、トークン量を節約する動機はない。**`max_tokens` は余裕を持って設定する。** 正規化・採点では 4,000 以上を目安とする。

### マルチモーダルモデルの扱い

利用可能なチャットモデル 9 種のうち 5 種がマルチモーダル対応である。しかし要件 11-2 により、**Street View の画像を AI へ送信しないため、これらの画像入力機能は使用しない。**

使用可能であっても規約上の判断で使わない、という設計上の選択である。

Embed API のキーは iframe の URL に含まれるため隠蔽できない。**HTTP リファラー制限が唯一の防御である**ため、キーを 2 本に分離し、Embed 用キーは Maps Embed API のみに制限する。メタデータ照会用キーはサーバ内に閉じる。

`.env` は Git 管理から除外し、`.env.example` のみを配置する。

## リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 構造化出力が未対応 | 正規化の信頼性低下 | 3 段階のフォールバックと Zod 検証。8/7 に検証 |
| pano ID の失効 | 出題が表示できない | 起動時に無料のメタデータ照会で検証、座標から再解決 |
| **エージェントが Street View Static API の画像取得を実装する** | **課金発生・規約違反** | 実装指示に禁止事項として明記。予算アラートを設定。差分レビューで確認 |
| エージェントのリクエスト消費が想定超過 | **レートリミットにより作業が停止**（課金は発生しない） | セッション前後で利用量を確認。1,200 超過時は手動実装へ切替 |
| 追い込み期間（8/17〜19）に枠切れ | 比較データが取得できず記事が書けない | 残枠 800 を切った時点でコーディングを別バックエンドへ退避 |
| `reasoning` 側に JSON が出力される | 正規化・採点のパースが失敗 | `content` が不正な場合を再試行対象とする。`reasoning` / `reasoning_content` 両方のキーを許容する |
| `max_tokens` を推論が食い潰す | `content` が空、または JSON が途中で切れる | `max_tokens` を 4,000 以上に設定する。トークン節約の動機はない |
| 提供終了モデルの指定 | API エラー | モデル名を実装指示に明記。過去記事の名前を流用しない |
| モデルごとのコンテキスト長超過 | HTTP 400 | `max_tokens` をモデルごとに設定する。`llm-jp` は 4,096 の制約がある |
| **総所要時間がタイムアウト（約 300 秒）を超える** | 504。ストリーミングでは `finish_reason` なしで打ち切られる | **1 リクエストの処理量を小さく保つ**（唯一の対処）。リトライしない（504 は枠を消費する）。`Kimi-K2.6` はバルク処理に使わない |
| **ストリーミングが HTTP 200 のまま打ち切られる** | 成功に見えるが本文が空。検出漏れの危険が最も高い | **`finish_reason` の有無を必ず検証する。** 所要時間やチャンク数で成否を判断しない |
| **構造化出力が件数を保証しない** | エラーなしで配列が 0 件や 1 件になり、静かにデータが欠損する | `minItems` / `maxItems` を指定する（実測で 6/6 改善）。ただし機構が不明なため**コード側でも件数を検証**し、不一致は再取得する |
| `finish_reason=length` による打ち切り | JSON が壊れてパース不能になる | モデルごとに `max_tokens` を調整する。`Qwen3.6-35B-A3B` は 8,000 では不足した |
| 採点の応答に 20〜30 秒かかり画面が固まって見える | 学習ツールとして使いづらい | ストリーミングで受信し進捗表示に使う。JSON 完成後にレンダリングする |
| 採点の応答が遅く実用性を欠く | 学習ツールとして使えない | 応答時間を計測ログに記録し、90 秒級のモデルを本番から除外する |
| 辞書生成のハルシネーション | 誤った知識を学習者に提示 | 複数モデル生成の不一致を人手確認対象として記録 |

## 実装時の禁止事項

コーディングエージェントへの指示に含める。

1. Street View Static API の**画像取得エンドポイントを呼ばない**（課金対象。メタデータ照会のみ使用可）
2. Street View の画像データを保存・キャッシュしない
3. Street View の画像を AI へ送信しない
4. 画像ファイルをリポジトリに追加しない
5. API キーをクライアント側のコードに直接書かない
6. 辞書外の用語 ID を生成・許容する実装をしない
7. 管理モードに一括承認機能を実装しない
8. 撮影年月を学習者向けの画面に表示しない（撮影年そのものがメタであり、答えを渡すことになる）
9. 著作権表記が Google 以外のパノラマを出題データに登録しない
10. **ベクトル埋め込み（embeddings）および RAG 機能を使用しない。** 用語辞書は 50 語規模であり、該当分をプロンプトに直接含めれば足りる。さらに[サービス基本情報](https://manual.sakura.ad.jp/cloud/ai-engine/01-basics.html)に「基盤モデル無償プランにおいても、RAG をご利用開始、すべてのドキュメントを削除するまで課金対象となります」と明記されている。**無償プランでも課金が発生するため、金銭面でも使用しない**
11. Playground から本番の検証を実施しない。Playground 経由の消費は計測ログに残らないため、スクリプトから呼び出す
